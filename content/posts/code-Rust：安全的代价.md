## Hello World

```rust
fn main() {
    println!("Hello, World!");
}
```

*这是 Rust 的 Hello World。乍一看它像 C——花括号、分号、main 函数。但它用 `fn` 声明函数，用 `println!` 这个带感叹号的宏来打印。第一眼它不惊艳，第二眼你会发现所有的细节都在暗示一件事：精确、安全、不妥协。没有隐式转换，没有未定义行为，没有垃圾回收。每一行代码经过编译器的时候，都会被一台看不见的机器逐字审查——这台机器的名字叫借用检查器。它严苛到让新手崩溃，但正是它让 Rust 成为了一门"跑起来就不会崩溃"的语言。*

![](/images/ferris-the-crab-rust.svg)

*Ferris the Crab——Rust 的非官方吉祥物。这只红色的螃蟹由 Karen Rustad Tölva 在 2010 年设计，后成为 Rust 社区最广为人知的象征。*

2006 年，温哥华，一栋公寓楼的电梯又坏了。

Graydon Hoare 背着包站在一楼大厅，盯着电子显示屏上那个一动不动的小箭头。电梯的控制软件是 C++ 写的。内存出了问题。这不是第一次了。大楼的管理员早就习惯了——每周至少宕一次机，维修工来重启一下，过两天又崩。

但今天是 Hoare 搬进来的第三周，他已经数不清这是第几次爬楼梯了。

他住在 21 楼。

大多数人遇到这种事，会在电梯口骂两句脏话，然后无奈地按亮手机，发一条推特抱怨公寓的物业管理有多烂。但 Hoare 不是大多数人。他是 Mozilla 温哥华办公室的一名软件工程师，专攻编译器和编程语言。他的脑子里没有脏话——他的脑子里有一个问题在翻来覆去地转：

**为什么 2006 年了，我们还在用一门三十年前的语言写电梯的控制软件？为什么这门语言连一块内存都管不好？**

他爬上 21 楼，推开家门，把包扔在沙发上，打开了笔记本电脑。他不是要给物业公司写投诉邮件——他是想试试能不能造出一门解决问题的新语言。

他想叫它 Rust。

这个名字来自一种真菌——锈菌。锈菌的生存策略不是"强"，是"过度设计以求生存"（over-engineered to survive）。它的孢子壁有好几层，能在极端环境下休眠几十年，等到条件合适再复活。Hoare 觉得这个名字完美地描述了他想做的事情：造一门硬到不可能崩溃的语言。

他不知道的是，这个在个人时间里开始的副项目，会在十五年后改变整个系统编程行业的方向。

## 带血的 C 和 C++

要理解 Rust 为什么诞生，你得先理解 C 和 C++ 统治系统编程三十年的代价。

C 在 1972 年诞生的时候，Kernighan 和 Ritchie 没有在语言里放垃圾回收器，因为 PDP-11 的内存只有 24KB，放不下一个运行时。C 让你直接操作指针——也就是内存地址。你可以把一个指针加一让它指向下一个内存位置，你也可以把一个整数强行解释成指针，指向任意一个地址。你甚至可以往已经释放了的内存块里写数据，然后在一百行之后才崩溃——如果它崩溃的话。这种设计对写操作系统的人来说是天堂：你可以控制每一比特。但对写业务逻辑的人来说，它是一种长期的折磨：你永远不知道自己有没有一个 off-by-one 的错误在等着引爆你的程序。

C++ 在 1985 年继承了这个传统，然后在上面加了一层又一层的抽象。它试图用面向对象来驯服复杂度，但它的内存管理依然是程序员的责任——"自己拿、自己还"。Bjarne Stroustrup 在他的书里写过："C++ 让写出糟糕的程序变得更容易"——这不是一句自嘲，他承认这门语言在给予力量的同时也给了开发者足够的空间伤害自己。

三十年过去了，整个行业为这个"自己管理内存"的设计付出了一笔谁都说不清的账单。

Microsoft 在 2019 年发布了一份让人不安的报告：在他们的安全响应中心（MSRC）追踪的所有 CVE（通用漏洞披露）中，大约 70% 是由内存安全漏洞引起的。不是业务逻辑的 bug，不是 SQL 注入，不是配置错误——就是简单的、老式的内存访问越界、空指针解引用、释放后使用。Google 的 Project Zero 团队也得出了类似的结论：Chrome 浏览器中大约 70% 的严重安全漏洞是内存安全问题。Apple 说他们的 iOS 和 macOS 中也差不多是这个比例。

这意味着什么？意味着整个互联网的基础设施——浏览器、操作系统、数据库、Web 服务器、物联网设备——都在一条用了几十年的旧地基上摇晃。我们往上面堆了无数的新功能、新框架、新架构，但地基的材料在 1972 年就被决定了，而且那层材料的设计目标不是"安全"，是"在 24KB 内存上能跑起来"。

## 来自过去的技术

Hoare 从 2006 年开始利用业余时间写 Rust。最开始他是在自己的笔记本里做的——一个 29 岁的 Mozilla 工程师，下班后在家里的电脑屏幕上敲代码。他没有告诉任何人他在做什么。前三年，Rust 甚至不是 Mozilla 的正式项目——它是 Hoare 的"20% 时间"项目（如果 Mozilla 有 20% 时间的话）。

编译器最初是用 OCaml 写的——大约 38,000 行代码。Hoare 选择 OCaml 是因为他熟悉函数式语言，而且 OCaml 的编译器工具链成熟，他能快速搭建一个原型。这个用 OCaml 写的编译器后来被抛弃了——Rust 在 2010 年左右自举了，也就是说它的编译器用 Rust 自己来编译自己。但这种"先用一门现有的语言造一个编译器，再用这个编译器编译自己，然后扔掉原来的编译器"的做法，是很多语言的常见路径。

Hoare 从一个令人惊讶的地方汲取了灵感：他不是从"未来"找答案，而是从"过去"。

他列出的影响语言清单听起来像是一份计算机历史博物馆的展品目录：CLU（1974 年）、BETA（1975 年）、Mesa（1976 年）、NIL（1981 年）、Erlang（1986 年）、Newsqueak（1988 年）、Napier（1988 年）、Hermes（1990 年）、Sather（1990 年）、Alef（1993 年）、Limbo（1995 年）。这些名字中有一大半在今天已经几乎没人用了。但 Hoare 从每一门里都提取了某种想法——CLU 的泛型、Erlang 的 actor 并发模型、Mesa 的异常处理、Newsqueak 的通道通信。他把这些碎片拼在了一起。

早期 Rust 开发者 Manish Goregaokar 后来用一句话评价了这件事："Rust 基本上是几十年老的学术研究。"

Hoare 自己的表述更诗意。他把 Rust 称作"来自过去的技术前来拯救未来于自身"（technology from the past come to save the future from itself）。这句话换个直白的说法就是：那些在 1970 年代和 1980 年代被学术界想出来、但因为性能或复杂度从来没能进入主流语言的好想法——Rust 把它们重新挖了出来，用一种务实的方式组装成了一个人人都能用的工具。

另外一个同样重要的影响来自 Cyclone——一门由 Lucent 和 AT&T 的研究人员在 2000 年代初期开发的安全 C 方言。Cyclone 的目标和 Rust 极其相似：在 C 的语法基础上添加内存安全机制，同时保留 C 的性能。Cyclone 引入了"区域内存管理"（region-based memory management）的概念——一种不在运行时做垃圾回收、而在编译时静态分析内存分配和释放的模式。Cyclone 最终没有成功——用户太少，工具链不完善——但它的许多思想直接影响了 Rust 的所有权系统设计。如果 Cyclone 没有失败，可能就没有 Rust。

Hoare 没有从零发明什么革命性的东西。他挖出来的都是别人已经想过的东西。区别在于——他的组装比任何人都做得更彻底、更决绝。

## Brendan Eich 的赌注

2009 年，Mozilla 正式注意到了这个偷偷进行的个人项目。

关键人物是 Brendan Eich——JavaScript 的创造者、Mozilla 的联合创始人兼 CTO。Eich 在 Mozilla 内部推动了对 Rust 的正式赞助，把 Hoare 的业余时间项目变成了 Mozilla 研究部门的正式项目。他的动机很简单：Firefox 是用 C++ 写的，而 Firefox 的安全漏洞清单长得令人绝望。Eich 想要一门安全的语言来重写 Firefox 的核心组件——或者至少，造一个能开发安全浏览器引擎的原型工具。

"Mozilla 做的事情里有很大一部分是在浏览器引擎领域，"Eich 后来说，"我们每天都在和越界访问、释放后使用这些问题搏斗。我们需要一种更好的方式。"

Eich 把工程师资源调到了 Rust 项目上。Patrick Walton——一个从编程语言博士项目中离开的年轻研究者——加入了。Niko Matsakis——一个在类型系统和内存管理方面有深厚学术背景的工程师——加入了。Felix Klock 从 Mozilla 的法国办公室加入了。Manish Goregaokar 也加入了。这支小团队在 Mozilla 总部 650 Castro Street 的办公区里霸占了一个会议室，门口挂了一块手写的牌子："the nerd cave"——极客洞穴。

说它是"洞穴"毫不夸张。那间会议室没有窗户，灯光惨白，白板上写满了类型签名和生命周期标注。团队成员大多是编程语言的研究背景——不是那种"写 Web 应用"的程序员，而是那种谈到 Hindley-Milner 类型推断时眼睛会发光的类型系统狂热分子。他们聚在这个没有阳光的房间里，用了几年时间，把 Hoare 的个人原型打磨成了一门真正的语言。

"那个房间又小又挤，但所有人都兴奋得不行，"Walton 后来回忆说。"我们那会儿的交流方式就是：在白板上写下代码，然后争论它应该怎么编译。经常一争就是一下午。"

这间"极客洞穴"后来成了 Rust 早期文化的重要象征——一群拒绝妥协的语言理论家，在 Mozilla 的庇护下，决心做一件没人做过的事。

## 所有权的诞生

Rust 最核心的设计——那个让它区别于所有前辈的东西——是它的所有权系统（ownership system）。

这个概念的来源可以追溯到 1970 年代线性类型（linear types）和仿射类型（affine types）的学术研究。线性类型的意思是：每个值必须被使用恰好一次——既不能多用，也不能不用。仿射类型放宽为"最多用一次"——你可以不用，但你不能用两次。这些概念在数学和逻辑学里有很深的基础，但几乎从来没有进入过主流工业语言。

Rust 的所有权系统是仿射类型思想在系统编程语言里的第一次大规模实战应用。

用最直白的方式来解释这个系统，大概是这样的：

在 Rust 里，每个值有且只有一个"所有者"（owner）。当这个所有者超出作用域时，这个值被自动释放——不需要垃圾回收器，不需要手动 `free`。如果你想从别的地方访问这个值，要么你把所有权"移动"给对方（原来的所有者不再拥有它），要么你把值"借用"给对方（你仍然拥有它，但对方获得了一个受限的引用）。借用的引用有一个"生命周期"（lifetime）——编译器在编译时跟踪它，确保它在值的有效期之内使用，不会在值被释放之后还在访问它。

听起来很简单？实际上不简单——这套规则的后果极其深远。

首先，它意味着内存安全被 100% 保证了——只要你遵守了 Rust 的规则，你的程序里就不可能出现空指针解引用、释放后使用、双重释放、缓冲区溢出这些经典的内存安全漏洞。不是"很少出现"，是不可能出现。因为编译器会在编译时拒绝任何违反规则的代码。

第二，它意味着 Rust 完全没有垃圾回收器的运行时开销。Java、Go、Python、Ruby 等语言都在运行时内置了垃圾回收器（GC），GC 负责自动回收不再使用的内存。但 GC 有时间开销（标记-清扫、引用计数）和空间开销（内存堆的管理结构）。Rust 的所有权系统在编译时就已经完成了所有的"谁该释放什么"的分析，运行时零开销。

第三，它意味着 Rust 是线程安全的。Rust 的类型系统确保了线程之间的数据共享必须通过特定的同步原语（`Mutex`、`Arc`、通道等），否则编译器会拒绝编译。这在 C++ 里是程序员自己负责的事——而在系统编程中，数据竞争是最大的 bug 来源之一，因为它在单次运行时可能永远不会出现，只有在特定时序下才会触发。

"Rust 的设计哲学是：不愿意在运行时付任何代价，"Niko Matsakis 在解释所有权系统时说。"所有你想要的安全性——内存安全、并发安全——都在编译时完成检查。如果编译器通过了，你的程序就是安全的。"

这套系统让 Rust 学习曲线陡峭到了令人绝望的程度。许多新程序员第一次遇到借用检查器（borrow checker）时，会经历一段先愤怒、再困惑、最终敬畏的心理过程。"与借用检查器搏斗"成了 Rust 社区经久不衰的自嘲 meme。社交媒体上流传着一个著名的梗图：一个程序员对着屏幕咆哮，旁边的标题是"不是我不同意借用检查器——是借用检查器不同意我"。

但 Rust 团队在这件事上极其坚定。2013 年——在 Rust 0.1 发布一年后——他们做了一个在所有主流语言设计史上都罕见的决定：**移除垃圾回收器**。早期的 Rust 实际上包含了一个可选的 GC——程序员可以选择用所有权系统，也可以选择回退到传统的垃圾回收。但在 2013 年，团队认为"可选的安全"意味着"不安全是默认选项"。他们删掉了 GC，让所有权系统成为唯一的路径。对于想要"简单"做法的人来说，这条门被彻底堵死了。留下的只有那座编译器。

这就像是 Rust 给自己的枷锁——但是那种你心甘情愿戴上的枷锁，因为它让你自由地写零运行时开销的底层代码。

## 火的试炼（2013-2015）

从 2012 年 1 月 0.1 版本公开发布，到 2015 年 5 月 1.0 正式稳定——这三年半是 Rust 最痛苦的成长期。

痛苦来自两个方向。一是内部的：团队在不断寻找"正确设计"的过程中，对语言做了翻天覆地的改变。早期 Rust 中的许多特性后来被移除了：`obj` 关键字（显式面向对象）被去掉了、typestate 系统（变量状态转换检查）被移除了、`pure` 关键字（纯函数声明）也被去掉了、各种专用指针类型（如 `~` 和 `@` 指针）被合并成了更统一的所有权模型。每做一次大的移除，都会赶走一批已经适应了旧版本的早期采用者。有一个笑话在当时的 Rust 社区里流传："你今天学的 Rust 语法，三个月后就不认识了。"

二是外部的：业界对 Rust 的态度是"看看再说"。2014 年 1 月，Dr. Dobb's Journal 的 Andrew Binstock 写道："Rust 被广泛认为是一门极其优雅的语言，但采用进展缓慢——因为它每版都在剧烈变化。"这句话既是客观描述，也是行业对一门不稳定语言的耐心极限测试。

但压力也在推动一件事：**找到真正的设计**。

2013 年，Graydon Hoare 做出了一个让整个社区意外的决定——他从 Rust 核心团队退出。原因不是吵架，不是失望——是因为项目长大了。Hoare 说 Rust 超出了一个人能控制的范围。他是一个语言设计者，但他不是团队管理者。Mozilla 的工程师们需要建立一个可持续的、社区驱动的治理结构。Hoare 选择了离开去"做其他好玩的事"（他后来去了 Apple 工作）。这让一些人担忧，但也让 Rust 的社区治理真正成熟了。

Hoare 退出之后，Rust 进入了一种有机的治理模式：一个核心团队（core team）负责整体方向，下面分设多个子团队——语言团队、编译器团队、库团队、工具团队、基础设施团队等。2014 年 3 月，Rust 引入了一个极其重要的社区治理工具——RFC（征求意见）流程。RFC 机制的玩法是：任何人对 Rust 的设计有重大修改建议，必须写一份 RFC 提交给社区讨论，经过评审和修改后才能被接受。这个机制后来被其他许多项目（包括 Go 和 React）借鉴，但 Rust 是最早把 RFC 流程系统化的大语言项目之一。

RFC 流程意味着两件事：第一，Rust 的设计不再是几个人在白板上画出来的——它是整个社区的集体智慧。第二，RFC 文档本身变成了 Rust 的活历史档案——每一份提案都记录了"为什么这么做"和"为什么不做别的"。后来当有人问"为什么 Rust 没有那个特性"时，只需要翻 RFC 记录就能找到答案。

2014 年的一个会议视频里，核心团队成员坐在一张长桌前，讨论着即将锁定的 1.0 特性。"这是我们最后一次可以改变设计的机会了，"Aaron Turon 在会上说。"1.0 之后，我们就只能添加，不能删除了。"

他们锁定的不仅仅是特性列表——他们锁定的是一个承诺：向后兼容。Rust 1.0 承诺，你现在写的代码在五年后、十年后还能编译。这个承诺在 C++ 的世界里几乎是不存在的（C++ 标准委员会经常在"破坏性改动"和"保守兼容"之间痛苦摇摆），但在 Rust 这里，它是一个底线。"在 1.0 之前，我们在寻找正确的设计；在 1.0 之后，我们在坚持正确的承诺。"

2015 年 5 月 15 日，Rust 1.0 正式发布。

那一天，全球的 Rustacean（Rust 爱好者的自称）——虽然人数还不多——在不同的城市举行了发布派对。旧金山、纽约、柏林、东京——十几个人到几十个人不等，聚在一起喝啤酒、吃披萨、然后念叨着他们等了六年的版本号："1.0"。

## Servo——浏览器中的试金石

Rust 有一个问题：它声称自己能写底层系统代码，但它从来没用它写过真正复杂的东西。它的所有权系统在白板上看起来很完美，但它能撑起一个浏览器引擎吗？

这就是 Servo 项目要回答的问题。

2012 年，Mozilla 研究部门启动了一个新的浏览器引擎项目——Servo。目标是从零开始，用 Rust 写一个完整的浏览器引擎。项目名字来自《神秘科学剧院 3000》（Mystery Science Theater 3000）中的机器人 Tom Servo——一个被队员们放在办公桌上的小玩具。

Servo 不是一个"在实验室里展览的学术演示品"——它是一个真正的、能渲染网页的浏览器引擎。Mozilla 想通过它来验证 Rust 是否真的能做最难的事情：解析 HTML、处理 CSS 布局、执行 JavaScript、渲染图形、响应鼠标事件——所有这些操作必须在同一个进程中流畅协同，同时保持全面安全。

Servo 团队和 Rust 团队在 Mozilla 内部是"互相喂养"的关系。Rust 团队添加一个新特性，Servo 团队立刻用它在真实浏览器中测试。Servo 团队遇到了 Rust 支持不够好的地方，回头给 Rust 团队提需求——"我们需要更好的并发支持""我们需要更灵活的 trait 系统""这个地方的编译器错误信息太让人困惑了"。

2013 年，Samsung 加入了 Servo 的开发。Samsung 对 Rust 感兴趣的理由不是"让互联网更安全"这种宏大叙事——他们有一个非常具体的商业需求：ARM 芯片上的移动浏览器性能优化。Samsung 的工程师们把 Servo 移植到了 Android 和 ARM 架构上，并尝试优化内存占用——这对于 Rust 的所有权模型来说是一个极佳的压力测试。

2016 年，Servo 的第一个公开版本发布了。它能渲染网页——虽然功能有限，但已经能跑。对于 Rust 团队来说，这是一个决定性的时刻：Rust 不是一门"只能写小玩具"的语言。它在实战中撑起了一个浏览器引擎。

但最大的考验是在 2017 年。Mozilla 在这一年发布了 Firefox 57——代号 Quantum。Firefox Quantum 的一个关键变化是：大量使用了从 Servo 项目中移植过来的组件。其中最重要的一个是 CSS 渲染引擎 Stylo——用 Rust 重写的 CSS 样式系统。Firefox 用户在这天打开浏览器时，如果不是被主动告知，根本不会注意到浏览器的内部已经换了一种语言——但他们会注意到一件事：Firefox 变快了，而且是肉眼可见的快。

"Rust 不仅仅是安全的——它让我们能够安全地并行化 CSS 样式计算，这在 C++ 里几乎不可能做到，"Mozilla 的工程师在发布时撰文写道。Firefox Quantum 的性能提升很大程度上来自于 Rust 的并发安全保证——因为 Rust 编译器保证了数据竞争不可能发生，工程师可以放心地把 CSS 计算工作分配到多个 CPU 核心上。在 C++ 里，同样的操作需要大量的手动锁管理，容易出 bug，而且维护成本极高。

这是 Rust 的第一个"生产环境大考"。它不是通过考试——是得了满分。

## Mozilla 裁员，Rust 的孤儿期

2020 年 8 月，一个消息震惊了 Rust 社区：Mozilla 裁员 250 人。

整个 Servo 团队被解散了。几十名 Rust 核心开发者——包括 Rust 编译器团队、库团队、工具团队中的 Mozilla 员工——被解雇了。一夜之间，Rust 的母公司——或者更准确地说，Rust 的"原生家庭"——失去了供养它的能力。

恐慌迅速蔓延。Rust 社区里充斥着各种猜测：Rust 会不会死？谁来维护编译器？谁来制定发展方向？一个被母公司抛弃的开源项目，历史上大多数结局都不太好——看看那些被公司放弃之后慢慢枯萎的项目就知道了。

但 Rust 没有死。原因是 Rust 在 Mozilla 之外已经积累了足够多的用户和贡献者。

疫情中的裁员后的第一周，Rust 核心团队发布了一份公开声明：Rust 不会消失。它正在加速 Rust Foundation 的成立计划——一个由多家科技公司共同资助的独立基金会，负责 Rust 项目的财务和治理。

2021 年 2 月 8 日，Rust Foundation 正式成立。五家创始公司是：Amazon Web Services、Google、Huawei、Microsoft 和 Mozilla。是的，Mozilla 依然在其中——但不再是唯一的支持者了。

"Rust 在今天已经超越了 Mozilla，成为了一个真正的社区项目，"Rust Foundation 的第一任执行董事 Shane Miller 在成立公告中说。"这些公司的支持确保 Rust 有了稳定的未来。"

这个名单揭示了一个重要的事实：Rust 不是 Mozilla 一个人的孩子了。AWS、Google、Microsoft——这些公司对 Rust 的需求比 Mozilla 更大，也更现实。它们需要 Rust 来写云基础设施、写操作系统组件、写数据库引擎。Mozilla 给了 Rust 出生，但这些巨头给了 Rust 抚养费。

没有人说得清楚 Rust 是从什么时候开始从"Mozilla 的实验项目"变成"整个行业的公共基础设施"的。但就在 2021 年，那个转折点清晰地到来了。

## 巨头入场

AWS 是最早大规模拥抱 Rust 的云服务商之一。他们的 Rust 团队从 2020 年开始快速增长，使用 Rust 构建了多个关键基础设施服务。AWS 的工程师在多个场合分享了他们的数据：Rust 代码在运行时的内存占用比等价的 Java 代码低了一个数量级，CPU 使用率降低了 30% 到 50%，而开发效率——一旦团队跨过了学习曲线——与 Java 相当甚至更好。AWS 还引用了一组来自葡萄牙研究者 2017 年的研究数据：Rust 代码的能耗比 Java 低约 50%，比 JavaScript 低一个数量级以上。"Rust 不只是安全和快速，"一位 AWS 工程师在博客里写道，"它是绿色计算的未来。"

Google 在 2021 年宣布 Android 开源项目正式支持 Rust 作为 C/C++ 的替代。理由很简单：Android 系统中的漏洞有大约 70% 是内存安全问题——这与 Microsoft 的数据几乎一致。Google 的工程师们做了计算：如果新代码用 Rust 写，这类漏洞会趋近于零。"我们用 Rust 写的代码，从 2019 年到 2021 年之间，在 Android 中产生了零个内存安全漏洞，"Android 安全团队的 Jeff Vander Stoep 在 2022 年 Google I/O 大会上宣布。这句话在安全社区里引起了巨大的波澜——因为没有任何一门主流语言能在做过如此规模的生产部署后说出"零个内存漏洞"。

Microsoft 也在做类似的事。Windows 内核的部分组件在 2023 年开始用 Rust 重写。Microsoft 的工程师们发现，许多经典的 Windows 安全漏洞——包括那些影响了 Windows 数十年之久的某些 bug 类型——如果用 Rust 写，在编译阶段就已经被借用检查器阻止了。2023 年的 BlueHat IL 大会上，Microsoft 安全响应中心的团队公布了一组数据：新引入 Windows 的 Rust 代码中的内存漏洞率为零。

但最具有象征意义的采纳发生在 2022 年底。这一年，Linux 内核在 6.1 版本中正式加入了 Rust 支持——由长期推动者 Miguel Ojeda 和他的团队经过数年的努力最终实现。Linux 之父 Linus Torvalds 对这个决定的态度是"谨慎但坚定"。"这不是在重写 Linux 内核，"Torvalds 在采访中说。"而是在让未来的内核代码可以多一个选择。如果你现在要写一个新的设备驱动，Rust 应该是一个有效的选项。"

这句话的意义无法被高估。Linux 内核是 C 语言最后的堡垒——一个由三十年间数千名贡献者用 C 写成的、数千万行代码的巨型系统。直到 2022 年为止，几乎没有人在严肃地讨论用 C 以外的语言写内核代码。Rust 打开了这扇门。不是以"替代"的身份——而是以"合作者"的身份。C 和 Rust 将在这个全球最重要的开源项目中共存。

## 安全有价

但 Rust 从来不是免费的午餐。它选了一条路，然后让所有人都看到了那条路的代价。

代价一：学习曲线。借用检查器是新程序员最痛苦的敌人。你在其他语言里写 `let x = vec![1,2,3]; let y = x; println!("{:?}", x);`——这段代码在 Rust 里不会编译，因为 `x` 的所有权已经在第二行被移动给了 `y`，第三行不能再使用 `x`。这个例子简单，但在实际代码中，类似的"所有权冲突"会出现在最意想不到的地方。你会发现自己反复与编译器对抗，反复写 `clone()` 来绕过借用检查，然后在深夜怀疑自己是不是选错了职业。Reddit 上的 Rust 版块里，有一类问题永远有人在问："我就想写一个链表，为什么这么难？"（答案：因为 Rust 的所有权模型显式地禁止了传统意义上"一个节点被两个地方引用"的内存布局。）《Rust 程序设计语言》被称为"与借用检查器搏斗的 500 页教程"不是没有道理——它确实需要那么多篇幅才能让普通程序员的大脑适应这套思维模式。

代价二：编译速度。Rust 编译器比 C++ 更慢，而且慢得明显。因为借用检查器和生命周期推断在编译时需要做大量的静态分析。一个中大型 Rust 项目的完整编译时间可能是等规模 C 项目的 3 到 5 倍。Rust 社区有自己的自嘲 meme：你去泡杯咖啡，回来 Rust 还在编译；你去吃个午饭，回来还在编译；你去休年假，回来——可能终于编译完了。当然，增量编译改善了这个体验——但"编译慢"仍然是 Rust 被反复提及的痛点。

代价三：生态从零开始。Rust 在 2015 年 1.0 发布时，`crates.io`（Rust 的包管理网站）上只有几千个包。和 Python 的 PyPI（数十万包）、JavaScript 的 npm（超过百万包）相比，这个数字几乎不值一提。生态系统需要时间积累——而在积累成熟之前，很多开发者做"要不要选 Rust"的决定时，第一反应是："我要的库有吗？"答案常常是"没有，需要你自己写。"

这三条代价加在一起，让 Rust 有了一个清晰的定位：它不是一门"你可以在一个下午学会"的语言。Matz 想让 Ruby 让人快乐，Rust 的设计者想让 Rust 让人安全——快乐和安全的优先级完全不同。Ruby 是一个"对开发者友好的运行时"；Rust 是一个"对编译器残酷的编译时"。

但代价带来的回报是什么？

2020 年，Discord 发布了一篇轰动业界的博客："为什么 Discord 从 Go 切换到 Rust"。他们的核心问题是 Go 的垃圾回收器——在 Discord 的实时消息处理场景中，GC 的暂停时间导致可见的延迟抖动。Discord 用 Rust 重写了核心组件后，性能提升了 10 倍。"Go 是门好语言，"Discord 的工程师写道。"但在我们的场景下，GC 的代价是不可接受的。Rust 让我们在保持安全的同时获得了 C 级别的性能。"

同年，Dropbox 宣布他们用 Rust 重写了核心同步引擎。原始的引擎是用 Python 写的——灵活、快速开发，但性能和可靠性无法支撑十亿用户级别的文件同步。Rust 重写后，性能提升了 4 倍，而更重要的提升是在稳定性上：内存越界相关的 bug 降到了几乎为零。

这些故事一次又一次地出现。Cloudflare 用 Rust 重写了他们的代理层。Figma 用 Rust 重写了他们的性能关键组件。AWS 用 Rust 写了 Nitro 安全芯片的控制软件。

每一个案例都在讲同一个故事：Rust 是贵的——但你花钱买的东西确实物有所值。

## 编译期付钱，运行时免费

这条口号——"pay at compile time, free at runtime"——并不是 Rust 官方宣传里的原话。它是社区从 Rust 的设计哲学里提炼出来的一个精辟总结。它抓住了 Rust 选择的本质：所有代价——所有的学习、所有的编译等待、所有的与借用检查器的搏斗——发生在你发布软件之前。发布之后，你的软件没有垃圾回收器、没有运行时检查、没有意外的内存错误。你在用户面前（在服务器上，在用户手机里，在电梯的控制芯片中）展示的是一个清零了内存安全问题的程序。

C 选择了"对程序员友好，对机器残酷"。你把所有责任放在运行时，但运行时崩溃的后果由用户承担。Java 和 Go 选择了"对运行时友好，对内存友好"——用 GC 帮你管内存，代价是额外的 CPU 和内存开销。Rust 选择了"对编译器残酷，对一切友好"——把安全检查前置到编译阶段，让运行时什么都不需要做，也什么都不需要担心。

这套哲学在 2006 年 Hoare 爬 21 层楼的时候就已经埋在他的脑子里了。十五年后回头看，它像一个预言：不是"我们能不能造一门更好的语言"，而是"我们愿不愿意为安全付出足够的代价"。

## 白宫说：用 Rust

2023 年到 2024 年之间发生了一件在编程语言历史上极其罕见的事：美国政府正式站台推荐一门编程语言。

美国国家安全局（NSA）在 2022 年底发布了一份关于内存安全的报告，明确建议开发人员从 C 和 C++ 转移到 Rust 等内存安全语言。2023 年，美国白宫国家网络总监办公室（ONCD）发布了一篇题为"Memory Safety: Past, Present, and Future"的报告，呼吁整个行业——特别是关键基础设施领域——采用内存安全语言。2024 年 2 月，ONCD 再次发布声明，重申了这一立场。

你不需要理解政治才能理解这件事的分量。美国政府——全球最大的软件采购方和网络安全标准的制定者——公开说："不要再写 C 了，用 Rust。"

这对于一门诞生产不足二十年的语言来说，是一种无法想象的认可。Fortran、C、C++、Java——它们都曾改变世界，但没有一门语言经历过"被美国政府公开推广"的时刻。

Rust 做到了。因为它恰好在一个特定的历史节点上——当整个行业终于意识到内存安全漏洞的代价可能比开发效率的代价更高——提供了一种以前不存在的选项。

## Rust 不杀 C

但是 Rust 不会终结 C。

三十亿行 C 代码运行在世界上的每一个角落——服务器、嵌入式设备、卫星、汽车的 ECU。这些代码不会因为 Rust 的流行而被重写。Linus Torvalds 说得很清楚："我们不是在重写 Linux 内核，我们只是给新的代码多了一个选择。"C 的负担——也是它的伟大之处——在于它几乎是所有硬件的"母语"。当一个新芯片诞生时，第一个编译器一定是 C 编译器。Rust 虽然在快速扩展支持平台，但它永远追不上 C 的覆盖面——至少在未来十年内。

Rust 真正改变的是新代码的选择。如果你 2024 年在 AWS 上写一个新的性能关键服务，你不会想到用 C++——你会想："Rust 行不行？"如果你在 Android 中写一个新的子系统，Google 的政策已经变成了"新代码优先选 Rust"。如果你在 Linux 内核中写一个新的设备驱动，Rust 已经是一个被官方支持的选项。

Rust 没有杀死 C——它让 C 从"唯一选项"变成了"遗留选项"。对一个一门语言统治了半个世纪的领域来说，这已经是一个足够惊人的成就了。

2026 年，Rust 1.95 发布了。Stack Overflow 的年度开发者调查中，Rust 连续多年排在"最受喜爱语言"的榜首。《The Rust Programming Language》已经被翻译成了二十多种语言。crates.io 上已经有了超过十五万个包。Rust Foundation 的成员公司已经扩展到了几十家。美国政府的报告里还在提它的名字。

而这一切的起点，是 2006 年温哥华一栋公寓楼的 21 层楼梯。一个程序员在爬完楼梯后打开电脑，开始造一门"过度设计以求生存"的语言。他可能没有意识到，那个让他愤怒的瞬间——一座电梯的 C++ 内存泄漏——会催生出一门被白宫推荐、被 Linux 接纳、被全球开发者连续多年评为"最爱"的语言。

Rust 选的路是"在编译期付钱，让运行时免费"。这条路不好走，但走的人越来越多。也许某一天，电梯的控制软件也会用 Rust 重写。到那时，Graydon Hoare 就可以安心坐电梯了。

## 人物

![](/images/graydon-hoare-rust.jpg)

**Graydon Hoare**—— Rust 的创造者。1977 年（？）生于加拿大。2006 年在 Mozilla 温哥华办公室工作时，因公寓电梯故障而开始设计 Rust。早期编译器用 OCaml 编写，自举后转向 LLVM。2013 年退出 Rust 核心团队，后来在 Apple 工作。名言："technology from the past come to save the future from itself"（来自过去的技术前来拯救未来于自身）。Rust 的名字取自"锈菌"——一种过度设计以求生存的真菌。

![](/images/brendan-eich-mozilla.jpg)

**Brendan Eich**—— JavaScript 的创造者、Mozilla 联合创始人兼 CTO。2009 年在 Mozilla 内部推动了对 Rust 的正式赞助。看到了 Rust 在浏览器引擎安全方面的巨大潜力——Firefox 的 C++ 代码库是内存安全的重灾区。安排了第一批全职工程师（Patrick Walton、Niko Matsakis 等）在 Rust 上工作。Eich 的支持让 Rust 从 Hoare 的个人项目变成了 Mozilla 的正式项目。

![](/images/niko-matsakis-rust.jpg)

**Niko Matsakis**—— Rust 核心团队关键成员，Mozilla 工程师。学术背景专注于类型系统和内存管理研究。在 Rust 的类型系统、所有权模型和借用检查器的设计中做出了关键贡献。Rust 社区中的"类型系统大脑"——他的博客《Baby Steps》是 Rust 深入技术讨论的首选来源。

![](/images/patrick-walton-rust.jpg)

**Patrick Walton**—— Rust 早期核心开发者。离开编程语言方向的博士项目加入 Mozilla 做 Rust 开发。参与了 Rust 几乎所有关键设计决策——从所有权系统到 trait 设计到并发模型。后来在 Meta 工作。被称为"Rust 的活历史"——他在 Mozilla 的 nerd cave 里度过了 Rust 成型期最关键的那几年。

![](/images/steve-klabnik-rust.jpg)

**Steve Klabnik**—— Rust 文档和社区核心人物。2012 年加入 Rust 社区，撰写了大量 Rust 文档，包括《The Rust Programming Language》（"TRPL"）的第二版——这是 Rust 社区最权威的教材。Rust 社区的文化塑造者之一，长期活跃在 Rust 论坛和会议演讲中。他将 Rust 定位为"一种让不可能出错的事情成为可能的语言"。

*Rust 的故事不是一匹黑马的逆袭——而是"系统编程三十年没有真正的替代者，今天终于有了一个选项"。C 不会消失，C++ 也不会消失，几十亿行旧代码还在跑。但所有写新的底层系统代码的人，都在严肃地考虑一件事：能不能不用 C 了？下一站，我们回到一切的起点——从 Fortran 到 AI，编程语言的七十年。七十年前，程序员在纸上写代码；今天，AI 替你写代码。这中间发生了什么？*
