这个栏目讲的是编程语言的故事。从 Fortran 到 Lisp，从 C 到 Java，从 Python 到 Rust——十五篇文章，十五种语言，每一篇都聚焦于一个瞬间：一个人面对一个问题，创造了一种新的方式让计算机理解人类。

但有一件事这些故事都没有讲：这些代码写出来之后，存在哪里？

在 Fortran 的年代，代码存在穿孔纸带上。在 C 的年代，代码存在磁带上和软盘里。在 1990 年代，开源代码散落在各种 FTP 服务器和邮件列表的附件里。你找到一个项目，下载一个压缩包，解压，读 README——如果项目不活跃了，你就再也找不到它了。

GitHub 改变了这一切。

它不是一门编程语言。它不发明新的语法，不设计新的抽象，不解决任何计算问题。但在这个栏目的故事序列里，它值得一个特别篇——因为所有其他语言的故事，最终都在这里交汇。你今天在任何一门语言中写代码——无论是用 Rust 写系统工具、用 Python 训练模型、用 JavaScript 构建网页——你几乎一定在用 Git 管理代码，一定在 GitHub 上分享它、讨论它、和别人一起维护它。

GitHub 没有发明编程语言，它发明了编程语言被使用的方式。

*GitHub 的 logo——一只长着章鱼触须的猫（Octocat），由设计师 Simon Oxley 在 iStock 上以 50 美元出售后被 GitHub 买断。这个融合了"章鱼"（octopus）和"猫"（cat）的生物，比任何代码都更准确地定义了 GitHub 的气质：友好、古怪、不装严肃——但它构建了全世界最大的代码托管平台。两百公里外，北极斯瓦尔巴特群岛的废弃矿洞里，GitHub Archive Program 正在把 21 TB 的开源代码保存在胶片上，预期保存 1000 年。*

## 帝国反击

2005 年 4 月 4 日，Linux 内核邮件列表炸了。

Larry McVoy，BitMover 公司的创始人，公开宣布收回 BitKeeper 对 Linux 内核开发团队的免费许可。BitKeeper 是一个商业版本控制系统——三年以来，它一直是 Linux 内核团队最核心的基础设施。Linus 和他的团队用 BitKeeper 管理着这个世界上最大的软件开发项目之一，每天有几百个补丁在被提交、审核、合并。它运行得很好。但 McVoy 受够了。

起因是一个叫 Andrew Tridgell 的人。Tridgell 是 Samba 项目的创始人——此人以"不逆向工程就睡不着觉"闻名。他编写了一个叫 SourcePuller 的工具，能读取 BitKeeper 仓库的元数据。McVoy 认为这违反了 BitKeeper 的许可协议——开源项目可以免费使用 BitKeeper，但你不能逆向工程它的协议。McVoy 打电话给 Linus 要求他制止 Tridgell 的行为，但 Linus 的态度是：我不能控制 Tridgell 做什么，而且我们确实需要一个工具来分析 BitKeeper 仓库的数据。McVoy 的回答很干脆：那我收回所有人的免费许可。

这不是一个小事。BitKeeper 是当时唯一一个真正支持分布式协作的版本控制系统。Linux 内核的 200 多名开发者遍布全球，他们依赖 BitKeeper 来同步彼此的代码。失去它意味着整个内核开发流程要回到 2002 年之前的状态——用邮件发送补丁包，用 `patch` 工具手工合并，用原始的方式人工记录版本历史。对于当时已经拥有超过 800 万行代码的 Linux 内核来说，这不是一次回退，是一次自杀。

Linus Torvalds 在邮件列表里的反应是标志性的：愤怒、直接、毫不拐弯。他骂 Tridgell 是个混蛋，但他也骂 BitKeeper 的许可条款有问题，骂整个开源世界的版本控制工具都是垃圾。然后他说了一句话，让整个邮件列表安静了半秒钟：

> "I will write a better one."

他要用两个星期写一个比 BitKeeper 更好的版本控制系统。开源世界的人都在问同一个问题：一个版本控制系统，能有多难写？

答案是：对 Linus Torvalds 来说，没有多难。他写了出来。名字叫 Git。

## 十天写出 Git

Linus 要解决的问题不只是"一个版本控制系统"。他要的是：分布式工作流、超高的性能、数据完整性高于一切——以及，最重要的一条原则："如果拿不准，就做和 CVS 相反的事。"

CVS 是当时最流行的开源版本控制系统，但从任何角度看它都是一个糟糕的设计——它不支持原子提交（多个文件的变化要么一起保存要么都不保存，CVS 做不到这一点），重命名文件会丢失历史记录，分支操作慢得让人发疯。Linus 觉得这东西不仅是糟糕的技术，更是一种对人的羞辱。他花了 Google Tech Talk 演讲的前半段骂 CVS 和 Subversion，然后才讲 Git——那句"如果你拿不准，就和 SVN 做相反的事"成了 Git 设计哲学最著名的概括。

Git 的开发从 2005 年 4 月 3 日正式开始。4 月 6 日，Linus 在邮件列表中宣布了 Git 项目——第二天就实现了自托管（Git 的代码用 Git 来管理）。4 月 18 日，Git 完成了第一次多分支合并。4 月 29 日的基准测试显示，Git 能以每秒 6.7 个补丁的速度往 Linux 内核树上打补丁——远超 Linus 设定的"不超过三秒"的目标。6 月 16 日，Git 成功管理了 Linux 内核 2.6.12 版本的发布——这意味着它已经可以处理这个星球上最复杂的软件开发项目了。

Linus 做了几个关键的设计决策。第一个也是最根本的一个——Git 不存"差异"（diff），存"快照"（snapshot）。前辈们——SCCS、RCS、CVS、Subversion——全部使用"增量存储"：它们保存文件的初始版本，然后记录每一次修改的差异。当你需要查看某个版本时，系统要追溯到初始版本，然后依次"叠加"所有的差异。Git 的做法完全不同：每次提交，Git 都会对整个代码仓库拍一张快照，保存所有文件的当前状态。如果文件没有变化，Git 只存一个指针指向之前那张快照。这个"愚蠢"的做法让 Git 的分支操作快到了极致——创建分支、切换分支、合并分支，都是毫秒级的操作。因为本质上是创建和移动指针。

第二，数据完整性靠 SHA-1 保证。Git 用 SHA-1 哈希算法为每个对象（文件、目录、提交）计算一个 40 位的十六进制校验和。任何一个比特的变化都会导致哈希值完全改变。这意味着 Git 仓库中的数据是不可篡改的——一旦提交，你就无法在不被察觉的情况下修改历史。对于 Linux 内核这种级别的项目来说，这是生死攸关的设计。

第三，分支是廉价的。在 CVS 和 Subversion 中，分支是一个"昂贵"的操作——通常需要复制整个目录树，而且合并分支是一场噩梦。在 Git 中，分支只是一个 41 字节的文本文件，里面记录了一个 SHA-1 哈希值。创建分支就是创建一个文件；切换分支就是改变 HEAD 指针。这个看似简单的设计，彻底改变了软件开发的工作流——让"频繁创建分支、合并、再创建分支"成为可能。正是因为分支变得廉价，Pull Request 这种协作模式才有了技术基础。

但 Linus 没有打算长期维护 Git。2005 年 7 月 26 日，他把 Git 的维护权交给了 Junio Hamano——一个来自日本的开发者，在 Git 项目上提交了大量代码。Linus 是 Git 的父亲，Hamano 是 Git 的养父。直到今天——二十一年后——Hamano 依然是 Git 项目的主要维护者，Google 支付他的薪水来全职做这件事。Git 从 Linus 手中那个"十天的原型玩具"成长为全世界最广泛使用的版本控制系统，绝大部分的工作是 Hamano 和社区完成的。

Git 赢了它当时的竞争对手 Mercurial。不单单是技术上更好——两者在设计上各有千秋，Mercurial 在 Windows 支持和 Python 扩展性上有优势，但 Git 在分支模型和性能上更强。Linus 的品牌效应和 Linux 内核团队的背书无疑加速了它的普及。但 Git 也在一个地方输得很惨：用户体验。它早期的命令行界面是出了名的难用。`git checkout`、`git reset`、`git rebase`——这些命令的语义复杂到让新手崩溃，让有经验的开发者也需要不时查手册。Linus 对此的态度很明确：Git 是为内核开发者写的，这些人能理解文件系统、数据结构和分布式系统。如果这让你不舒服，你不是 Git 的目标用户。

这种态度把这个故事的下一章推到了舞台上。当 Git 在服务器上跑起来之后，同样被它的潜力吸引的人开始在它上面"盖楼"——让 Git 变得对普通人可用。这些人不是内核开发者，他们是 Ruby 黑客、Web 设计师、独立开发者——他们看到了 Git 的底层强大，也看到了它的表层丑陋。他们想在上面建一个漂亮的东西。

## 版本控制的黑暗时代

但 Git 不是凭空产生的。在它之前，人类用了几十年的时间来寻找一种"多人协作写同一份代码"的方法。每一种方法的失败和新方法的诞生，都在降低协作的门槛——而这是整篇文章的暗线。

1972 年，贝尔实验室的 Marc Rochkind 发明了 SCCS（Source Code Control System）。这是世界上第一个版本控制系统。它解决的问题非常简单：当两个人同时修改同一个文件时，如何避免一个人覆盖另一个人的工作？SCCS 用了一个暴力的方法：锁。你想修改一个文件，先把它"锁定"，改完之后再解锁。其他人只能干等。这个设计反映了一个时代的假设：代码是一个人写、另一个人偶尔帮忙的工作。它不是协作工具，是一种防冲突装置。

1982 年，Walter Tichy 在普渡大学发明了 RCS（Revision Control System）。它比 SCCS 更轻，但仍然工作在单个文件的层面上。RCS 的贡献在于它引入了"检出-修改-检入"的循环——你不需要一直锁着文件，只需要在修改完成之后把结果"检入"到系统里。但它依然没有解决多人并发修改的问题——如果你和别人同时改了同一个文件，RCS 会让你手工合并。

1986 年，CVS（Concurrent Versions System）诞生了。这是一个里程碑：它是第一个允许"同时编辑、事后合并"的系统。CVS 的模型是这样的：每个人都从中央服务器"检出"一份代码的副本，各自修改，然后各自提交。如果两个人的修改冲突了，CVS 会尝试自动合并；合并不了的，手工解决。这个模型在 1990 年代到 2000 年代统治了开源世界——SourceForge 用的就是 CVS。但 CVS 有致命的缺陷：不支持原子提交、重命名就是灾难、分支操作慢得让人崩溃——而且它假设"世界上有一个唯一的中央权威"。

2000 年，Subversion（SVN）出现了，试图修复 CVS 的所有问题。它做到了原子提交、更好的目录管理、更快的性能。但它犯了一个和 CVS 一样的根本错误：它是集中式的。在 SVN 世界里，所有代码的"真相"都存在中央服务器上。你需要联网才能提交。如果你离线——在飞机上、在家里、在地铁里——你只能对着本地修改叹气。更重要的是，SVN 保留了开源项目中的一个隐形的等级制度：只有少数"被信任的开发者"拥有提交权限，其他人只能把补丁通过邮件发给维护者，然后等待。

十年来，数以万计的开源项目用着这套流程：发现 bug → 下载源码 → 修改 → 生成 patch → 发给邮件列表 → 等待被注意。如果你的补丁没有被注意——这经常发生——它就会淹没在邮件列表的数百封未读邮件里，永远地消失。这不是技术问题，这是一个社会学问题：版本控制系统设计的前提是"少数人审查、多数人贡献"，但开源世界需要的是"每个人都是平等的参与者"。

2002 年，Larry McVoy 的 BitKeeper 第一次让分布式协作变得真正可用。BitKeeper 没有一个中央真相——每一个人都有一个完整的代码仓库。你可以在离线状态下做任何操作（提交、分支、合并、查看历史），然后在有网络的时候和其他人同步。对于 Linux 内核这种由几百个独立开发者组成的松散团队来说，它是完美的工具。这也是为什么 2005 年 BitKeeper 许可危机如此令人愤怒——不是因为开源社区失去了一个工具，而是他们终于体验过更好的协作方式后，又被迫回到了黑暗时代。

然后 Git 来了。Git 不仅做到了 BitKeeper 能做到的一切，还做得更好、更快、更安全——而且开源。但 Git 只是工具，不是平台。有了铁路之后，还需要火车站——需要一个地方让所有列车停靠、让旅客上下、让时刻表被查看到。这个"火车站"在 2007 年秋天的一个酒吧夜晚被画出了草图。

1972 年的 SCCS 是世界上第一个版本控制系统。版本控制的故事从这里开始。每一种新工具都在回答同一个问题：多个人怎么在同一份代码上工作而不互相覆盖？Git 给出的终极答案是："每个人都有一个完整的仓库。"

## Zeke's Bar 那一夜

2007 年 10 月 18 日，旧金山 SOMA 区，Zeke's Sports Bar and Grill。

这是一条不起眼的街——第三街，距离 AT&T 球场几个街区，平时是一个体育酒吧。但周四晚上它不是体育酒吧，它是 Ruby 程序员的秘密据点。那一天晚上的活动叫"I Can Has Ruby Night"——一个半私密的 Ruby 黑客聚会，基本流程是写代码、喝酒、再写代码、再喝酒。参加者中有一个 28 岁的年轻人叫 Tom Preston-Werner，他是 Powerset（一个自然语言搜索引擎初创公司）的工具开发者，Ruby 社区的活跃成员。另一个是 Chris Wanstrath，刚 22 岁，在 CNET Networks 工作，也是一个 Ruby 黑客。两人之前见过面，但算不上朋友——顶多是那种"嘿，我觉得你的代码写得很棒"的点头之交。

晚上某个时刻，Preston-Werner 一个人坐在包厢里，刚点了一杯 Fat Tire 啤酒。他需要一个休息。几周前，他开始了 Grit 这个项目——一个用 Ruby 以面向对象的方式访问 Git 仓库的库。当时 Ruby 社区里认真用 Git 的人很少，Wanstrath 是其中之一。Preston-Werner 看到他走进来，把他拉到包厢里："兄弟，你看这个。"他打开笔记本电脑，开始展示 Grit 的代码。展示的东西其实不多——一个库的早期原型——但 Wanstrath 的眼睛亮了。Preston-Werner 感到时机到了，说出了那个半生不熟的想法："我想做一个网站，给程序员分享 Git 仓库用的。就叫 GitHub。"

Wanstrath 的反应据回忆是带着一种非常激动的语气说的："我加入，干吧。"

第二天的晚上——2007 年 10 月 19 日晚上 10 点 24 分——Chris Wanstrath 往 GitHub 仓库里做了第一个 commit。这个 commit 在数码石块上刻下了一句"这是个开始"。没有股权协议，没有商业计划书，没有法律文件。两个年轻人决定一起做一些很酷的东西。

接下来的三个月，他们过着疯狂的生活。Preston-Werner 在 Powerset 做全职工作，Wanstrath 在 CNET 做全职工作。每个周六他们见面开会聊功能和定价。旧金山的雨季很长，有一次他们在一家越南春卷店里讨论了两个小时定价策略——最后决定用这个公式：公共仓库免费，私有仓库按月付费，每个月 7 美元起。在那个"免费互联网"的黄金年代，他们坚持要收费。这个决定后来被证明是 GitHub 活下来的关键——他们有收入，不需要烧投资人的钱。

2008 年 1 月进入私人 beta 测试，邀请朋友加入。二月，PJ Hyett 加入团队，成为第三位联合创始人。四月十日，GitHub 正式公开上线。他们没有邀请 TechCrunch——不是因为他们不想，是因为他们觉得"我们的用户会自己找过来"。他们是对的。GitHub 在第一个月就积累了用户，而且这些用户是真的在使用——不是注册了放着，是真把自己的代码放上去。

但 Preston-Werner 还有一个问题：他还在 Powerset 上班。2008 年 7 月 1 日，Powerset 被微软以大约 1 亿美元的价格收购。微软向 Preston-Werner 伸出了橄榄枝：如果他留下来做微软员工，三年内给他 30 万美元的留任奖金加股票期权。对于一个 29 岁、已婚、从哥斯达黎加野外考察回来的妻子需要安家的男人来说，这几乎是一道不用思考的选择题——他可以在 GitHub 和微软之间选一个。微软那边是"安全的、确定的大笔收入"；GitHub 这边是"不确定的、未知的、可能什么都没有的收入"。

他选择了 GitHub。

他在博客里写下了那个决策背后的心理活动，有一段后来被无数创业者引用："当老去的那天，我想回头看自己的人生说'哇，那真是一场冒险'，而不是'哇，我真的很安全。'"他拒绝了微软的 offer。他在 Powerset 的最后一天，老板让他交出工牌和笔记本电脑，他走出办公室，走上旧金山的街头，感到恐惧和自由同时袭来。32 岁的他第一次没有工资拿，只有三个合伙人的公司和一个还不够稳定的网站。但他相信一件事：Git 是未来——而 GitHub 是让 Git 变得对每个人都可用的工具。

旧金山 SOMA 区的 Zeke's Sports Bar and Grill。2007 年 10 月的一个"I Can Has Ruby Night"，Tom Preston-Werner 和 Chris Wanstrath 在这里构思了 GitHub。一个本来半生不熟的想法变成了改变软件行业的东西。

## Pull Request——社交编程的杀手锏

GitHub 真正的创新不是 Git 托管，也不是漂亮的 UI——虽然它们确实比 SourceForge 和 Google Code 好了太多。GitHub 真正的创新叫 Pull Request。

这是一个简单到让人想"为什么以前没人做"的概念。用 Git 来说，就是：你 Fork（复制）了一个项目，做了修改，然后向原项目发出一个请求，希望维护者把你的修改合并进去。体现在 GitHub 的界面上，它是一个干干净净的按钮——"New Pull Request"。点击它，你输入的是一段描述你修改了什么的文本；提交出去，项目维护者接收到的是一个完整的、附带了代码 diff 的"请审查并合并"的请求。

在 GitHub 之前，给开源项目贡献代码的流程是：发现 bug → 下载源码压缩包 → 解压 → 修改 → 生成一个 patch 文件 → 发到邮件列表 → 等待维护者注意 → 如果幸运，被注意了 → 维护者手工测试 → 如果通过了，合并。整个过程最长的一步是"等待被注意"。大多数贡献者死在这一连串的步骤里——不是因为他们不想贡献，而是因为"给一个陌生项目发 patch"的心理门槛太高了。

在 GitHub 之后，流程变成了：Fork → 修改 → Pull Request → 讨论 → Merge。Fork 不再是威胁——它是协作的前提。在 1990 年代的开源世界里，"Fork"是一个带着恶意的词。它意味着分裂、社区撕裂、资源分散——Unix 在 1980 年代的碎片化是所有开源社区的一个噩梦。当一个人"Fork 了一个项目"，他的潜台词是"我不信任你的方向，我要自己来"。但 GitHub 把 Fork 的意思从"我要和你对着干"变成了"我想帮你更好"。Fork 变成了"复制"——是一个完全无害的操作。每个人都可以有自己的一份副本，可以随意修改，不用担心破坏原始项目。如果你做出了好的改动，你提交一个 Pull Request——原维护者可以选择接受或拒绝。如果被拒绝，你的 Fork 依然存在，你依然可以继续你的分支。

GitHub 的 slogan 从一个技术事实变成了一个社会学宣言："Fork 是新的贡献。"

这个故事有一个关键的标志性案例：Ruby on Rails。Rails 是 2000 年代后期最有影响力的 Web 框架之一，它的社区从一开始就拥抱了 Git 和 GitHub。2008 年 4 月，Ruby on Rails 成为第一个迁移到 GitHub 的大型项目。DHH（David Heinemeier Hansson）把 Rails 的代码从 Subversion 搬到了 GitHub——这不是一个简单的仓库迁移，是整个社区协作方式的转型。Rails 的 Pull Request 成了 GitHub 的活广告——同时期其他开源项目看到 Rails 社区那种"人人可贡献、贡献即讨论"的氛围，纷纷跟进。Python 来了，Node.js 来了，jQuery 来了，Twitter 的 Bootstrap 来了。到 2010 年代初，"GitHub 上有这个项目吗"已经成了开发者判断一个开源项目是否活跃的首要标准。

GitHub 早期的 Pull Request 界面简洁到极致——一个描述框、一个"Create pull request"按钮、下面就是讨论串。这个简单的界面改变了全世界开发者协作的方式。

## 从工具到平台

但光有 Pull Request 是不够的。GitHub 的崛起还有三个更深层的原因。

**第一，发现。** GitHub 让开源项目可以被找到。在 SourceForge 时代，找到一个好项目的唯一方式是去 SourceForge 主页翻列表，或者去 Google 搜。GitHub 做了 Explore 和 Trending 页面——你可以按语言、按热度、按更新时间来浏览项目。Stars 替代了"下载量"成为衡量项目受欢迎程度的标准——而 Star 不是一个技术指标，它是一个社交指标。你给一个项目点 Star，相当于 Facebook 的"点赞"——你在告诉世界"我觉得这个项目不错"。每一个 Star 都在 GitHub 的社交图谱上增加了一个节点。

**第二，身份。** GitHub 个人主页成了程序员的新简历。在开源社区的早期年代，一个程序员的简历上写的是"精通 C++、Java，5 年工作经验"。到了 2010 年代，招聘者的第一反应变成了"给我看看你的 GitHub"。你的 commit 历史、你参与的项目、你提交的 Pull Request——这些东西比任何面试话术都更真实地反映了你的能力。GitHub 把"谁在写代码"这个问题的答案从"简历上的陈述"变成了"可公开审计的公开记录"。这是一个深刻的权力转移——用人单位不再需要相信你的简历，他们可以去查你的 Git 日志。

**第三，生态。** GitHub 不停地往平台上"加层"。Issues 让 bug 追踪不再是独立的系统。Wiki 让项目文档和代码住在一起。GitHub Pages 让每个项目都能有一个网站——用 Jekyll 静态生成器，把 Markdown 文件直接变成页面。Code Review 让每段代码被合并前都能像真正的"同行评审"一样被审查——在 Pull Request 页面里逐行评论，让代码审查不再需要额外工具。2019 年推出的 GitHub Actions 更是把 CI/CD（持续集成/持续部署）直接嵌入了平台——你再也不需要 Travis CI、Jenkins 或 CircleCI 了。GitHub 不是一个"存代码的地方"——它是一个完整的软件开发操作系统。

GitHub 赢在了"接管了开发者工作流的每一个环节"。你在这里发现项目，在这里阅读文档，在这里报 bug，在这里提交代码，在这里讨论设计，在这里审查修改，在这里构建发布——甚至在这里托管你的个人主页、管理你的开源财务（GitHub Sponsors）。开发者从"要搭配五六个工具才能工作"变成了"一个 GitHub 就够了"。

在这种背景下，GitHub 的文化也非常特别。公司是扁平化的——没有中层管理者，没有考勤制度，不记录休假天数。员工叫自己"Hubbernauts"（GitHub 宇航员）。办公室里没有封闭的经理办公室——所有人，包括 CEO，都在开放工位上工作。公司有 kegerator（啤酒机），四连装的。会议室的名字来自电影（比如"白宫战情室"的低预算仿制版）。WIRED 杂志 2012 年采访时报道了一个场景：GitHub 的 CTO 在开放式办公区高声放着 LCD Soundsystem 乐队的歌，程序员们在显示器前戴着耳机写代码——有人在下午三点走了，有人在半夜十二点来了。没有人打卡，没有人问。

但 2014 年，这个文化出现了裂缝。联合创始人 Tom Preston-Werner 被指控骚扰——后来调查没有结论，但他辞去了 CEO 职位。Chris Wanstrath 接任。这是 GitHub 第一次从一个"四个好朋友做的公司"转向更正式的管理结构。中层管理者被引入了。开源社区的理想主义和商业化公司之间的张力开始被更严肃地对待。

GitHub 在旧金山 SOMA 区六公寓（Six Apart）原址的办公室，14000 平方英尺的"极客天堂"。开放式办公区、项目室里的四连装啤酒机、会议室里挂着穿着拿破仑装的 Octocat 画像。

## Octocat 与北极存档

三个故事最能代表 GitHub 的文化符号、文明愿景和规模效应。

**第一个是 Octocat——那只章鱼猫。**

2007 年，一个叫 Simon Oxley 的英国图形设计师在 iStock（一个卖免版权图片的网站）上传了一张卡通图。它看起来像一只猫，但长着八条章鱼一样的腿，表情呆呆的。Oxley 管它叫 Octopuss（章鱼猫）。标价大约 50 美元。

GitHub 当时正在找 logo，看中了这幅图。但 iStock 的许可证不允许把图片用作 logo——GitHub 要买断它。他们联系了 Oxley，谈了一个买断价格。价格没有被公开过，但据推测在数千到数万美元之间——对 iStock 上的一张 50 美元 clip art 来说，这是一个不错的交易。Oxley 后来还卖过另一张图给 Twitter——那只简笔画小鸟。是的，Twitter 的 logo 也是他设计的。

GitHub 把 Octopuss 改名叫 Octocat，注册了商标。后来他们请了插画师 Cameron McEfee 来为 Octocat 设计各种变体——穿不同的衣服、做不同的表情、出现在不同的场景里。到今天，Octodex（Octocat 的"多形态图鉴"）里有了成百上千种 Octocat 变体。它是软件行业中最著名的吉祥物——可能是唯一一个从 50 美元的 stock photo 变成了拥有注册商标和全球化知名度的品牌形象。

**第二个是 GitHub Archive Program——北极存档计划。**

2020 年 7 月，GitHub 做了一个让很多人吃惊的事情：把所有活跃的公共开源代码——21 TB 的数据——储存在了挪威斯瓦尔巴特群岛的一个废弃矿洞里。这个矿洞靠近北极，环境寒冷、干燥、稳定。不远处就是斯瓦尔巴特全球种子库——那些储存植物种子的地窖。

代码被保存在特制的 piqlFilm 胶片上——每一帧都是一张高密度二维码矩阵。每张胶片能存储大约 88 个 100MB 的文件。整个存档用了 186 卷这样的胶片，被装在一个特制的钢制容器里，埋在矿洞里。预期保存时间是 500 到 1000 年。

GitHub 还和微软的 Project Silica 研究合作了另一个更疯狂的项目：把代码写入石英玻璃的内部，通过激光改变玻璃分子结构来编码数据。理论上的保存时间：10000 年。

这个项目的意义不在于实际用途——谁会在 500 年后去北极挖矿洞读代码呢？它的意义在于象征。GitHub 在说：开源代码不是一个网站的存量，它是人类文明的一部分。这些代码值得像种子一样被保存。

**第三个是规模——一亿人。**

2023 年 1 月，GitHub 宣布平台上有超过 1 亿开发者用户。2025 年 5 月，这个数字达到了 1.5 亿。全球大约每 50 个人里面就有一个 GitHub 账户。仓库数量在 2025 年突破了 10 亿个——其中第 10 亿个仓库是一个恶搞：里面只有一行字 "shit"。

但这个规模也带来了问题。GitHub 成了一座"围墙花园"——它太大了，以至于"开源"和"在 GitHub 上"几乎成了同义词。如果你的代码不在 GitHub 上，它几乎不存在于开发者的视野中。GitLab、Bitbucket、SourceHut 等竞争对手虽然在成长，但和 GitHub 的差距仍然很大。当一个平台占据了如此主导的地位时，开发者社区的健康就依赖于这个平台的善意——而善意是容易被商业化驱动的决策侵蚀的。

Simon Oxley 在 iStock 上出售的原始 Octopuss 设计，标价约 50 美元。GitHub 以买断价格获得后改名为 Octocat，成为了全世界最知名的技术吉祥物。

## 微软的拥抱

2018 年 6 月 4 日，全世界开发者收到了一个让他们心脏漏跳一拍的消息：微软以 75 亿美元收购 GitHub。

整个开源社区的反应是高度一致的："完了。"在此之前，微软对待开源的态度可以用五个字总结："视 Linux 为癌瘤。"前 CEO Steve Ballmer 在 2001 年说过这句著名的话。微软曾经用尽一切手段阻止开源软件的发展——专利威胁、FUD（恐惧、不确定和怀疑）宣传、专利侵权诉讼。现在这个公司要买下开源世界最大的代码托管平台？

社交媒体上出现了#MovingToGitLab 的 hashtag。GitLab 的 CEO 在当天宣布了"有史以来最大规模的项目迁移潮"——超过 10 万个仓库在收购消息公布后的 24 小时内从 GitHub 迁移到了 GitLab。Bitbucket 也报告了类似的数据。

但事情没有像悲观者预测的那样发生。

2014 年上任的微软 CEO Satya Nadella 改变了一切。Nadella 的战略核心是"云优先、移动优先"——而云意味着拥抱开源。在他的领导下，微软做了很多 Steve Ballmer 时代不可想象的事情：.NET Core 开源并跨平台、SQL Server 支持 Linux、VS Code 基于 Electron 开源框架构建、PowerShell 开源并支持 Linux。微软自己的代码（.NET Core、VS Code、TypeScript、PowerShell）全部放在了 GitHub 上。到 2016 年，微软已经是 GitHub 上组织贡献者数量最多的公司——超过了 Google、Facebook、Amazon。

收购 GitHub 是 Nadella 战略的自然延伸：如果开源已经不可逆转，为什么不拥有它的基础设施？

更重要的是，收购后的 GitHub 没有死。微软任命了 Nat Friedman——Xamarin 的联合创始人、一个开源出身的 CEO——来领导 GitHub。Friedman 和后来接任的 Thomas Dohmke（同样是 Xamarin 背景）都来自跨平台、开源的世界。他们带来的改变是 GitHub 历史上的一个重要转折：GitHub Actions（2019）、GitHub Codespaces（2021）、GitHub Copilot（2021）——这三个最重要的新产品全是微软旗下的 GitHub 做出来的。前两个是基础设施的强化，第三个则彻底改变了写代码这件事本身。

Copilot 的技术预览基于 OpenAI Codex——一个在数十亿行公开代码上训练出来的 AI 模型。它在 2021 年 6 月发布时，让整个行业看到了"AI 辅助编程"的初步形态：你在编辑器里写注释，Copilot 帮你补完代码。你写半个函数，它帮你补全剩下的一半。它不是完美的——生成的代码有时是错的、有漏洞的、有版权问题的——但它在 2024-2025 年已经迭代到了让很多开发者"没有 Copilot 就不会写代码"的程度。

争议也随之而来。GitHub Copilot 的训练数据来自 GitHub 上的公开仓库——包括那些使用 GPL 或 MIT 许可的代码。版权问题直到 2026 年仍然没有完全解决。开源社区的怨恨不只来自版权——有些人觉得 GitHub 把他们的免费代码变成了微软的收费产品。2022 年，GitHub 与 ICE（美国移民和海关执法局）的合同被曝光，引发了公司内部员工的大规模抗议。GitHub 的"不作恶"叙事在成为大公司的一部分后变得越来越难以维持。

但不可否认的是，被微软收购后的 GitHub 活了下来，而且活得很好。

![](/images/satya-nadella-github-acquisition.jpg)

*2018 年 6 月 4 日，微软宣布以 75 亿美元收购 GitHub。CEO Satya Nadella 把这笔交易定位为微软"拥抱开源"战略的终极标志。收购后的 GitHub 没有按悲观者的预期消失——它长出了 Copilot、Actions、Codespaces。*

## 后记——代码的社交网络

从 2005 年 4 月 Linus Torvalds 敲下 Git 的第一行代码，到 2007 年 10 月旧金山的酒吧里 GitHub 被构思出来，再到 2026 年 GitHub 拥有超过 1.5 亿用户——二十一年的时间，这个故事的明线是一条清晰的技术进化路径：BitKeeper 危机 → Git 诞生 → GitHub 平台 → 微软收购 → AI 编程。但暗线始终没有改变过——协作的门槛在不断地降低。

1991 年，Linus Torvalds 在 comp.os.minix 新闻组上公布 Linux 时说："这只是我的个人爱好，不会成为什么大型、专业的东西。"今天，一个 14 岁的学生可以在 GitHub 上 Fork 整个 Linux 内核，修改一段代码，提交 Pull Request——如果他的修改是好的，它会进入下一版 Linux 内核，运行在全世界几十亿台设备上。不需要成为内核开发者，不需要被 Linus 信任，不需要在邮件列表里推销你的 patch。只需要一个 GitHub 账户，一次点击，几行描述。

这就是"社交编程"的本质：不是"代码在社交"，是"编程的门槛被社交化了"。GitHub 没有发明分布式版本控制——Linus 已经做了。GitHub 没有发明 Git——Linus 已经做了。GitHub 做的事情是把这个复杂的底层工具包上了一个"社交层"——用图形界面隐藏命令行参数，用 Fork 按钮抹去了 permission denied 的焦虑，用 Pull Request 取代了"你能不能把我的 patch 看一遍"的卑微请求。每一个设计都在降低"和其他人协作写代码"的心理门槛和操作成本。

GitHub Copilot 的出现让这个暗线走到了一个奇异的终点——协作的对象不再只是人类了。AI 开始写代码，Pull Request 里出现了机器人的名字。2025 年，GitHub 上的 AI 生成代码已经占到了所有新提交的显著比例——没有人知道确切数字，但所有人都感受得到变化。代码不再是一个人类一句一句敲出来的东西，它是人类和 AI 对话的产物。"社交网络"从"程序员与程序员之间的连接"变成了"程序员、AI 和代码之间的三重连接"。

但这也正是"降低门槛"这条暗线的最终形态。写代码曾经是数学家的特权——Fortran 年代你至少需要理解浮点运算和纸带读取。写代码后来成了程序员的职业——你需要学好 C、Java、Python 才能找到工作。写代码现在正在变成任何会说话的人都能做的事——你说出需求，AI 帮你写成代码。GitHub 从一个"给程序员用的社交网络"变成了"代码之所以存在的基础设施"。

这个故事不属于任何一种编程语言——它不属于 C，不属于 Ruby，不属于 JavaScript。但所有编程语言都被它改变了。没有 Git，Linux 的发展速度会慢很多。没有 GitHub，Python、Rust、TypeScript 的社区发展可能完全不同。没有 Pull Request，开源项目的协作方式可能还停留在"发邮件给维护者"的黑暗时代。

GitHub 没有发明编程语言——它发明了编程语言被使用的方式。

2026 年，GitHub 的 Octocat 依然在每一个页面的左上角朝你眨眼睛。北极的矿洞里，21 TB 的开源代码静静地躺在胶片上，等待一个可能永远不会到来的读者。每天，数以百万计的开发者们在世界各地 Fork、Clone、Commit、Push、Pull Request——这些动词已经变成了软件开发者的通用语言，就像"Google 一下"变成了搜索的同义词一样。

下一个二十年会发生什么？当 AI 写的代码占主流时，人类还在一起"社交编程"吗？答案可能微酸——但 GitHub 仍然是那个舞台。代码不再只是代码了——它是对人类如何组织大规模协作的一次持续二十一年的实验。这个实验的结论是：降低门槛，让更多人参与进来，好事情就会发生。

这不是一门编程语言的故事。但它是所有编程语言的故事。

![](/images/linus-torvalds-young.jpg)

**Linus Torvalds（1969–）** —— Linux 内核的创造者，Git 的创造者。2005 年因 BitKeeper 许可危机用两周时间写出了 Git 的原型。设计哲学："如果拿不准，就做和 CVS 相反的事。"2005 年 7 月将 Git 维护权交给 Junio Hamano。至今仍在维护 Linux 内核。

![](/images/junio-hamano-portrait.jpg)

**Junio Hamano** —— Git 的"养父"。2005 年 7 月从 Torvalds 手中接管 Git 维护权至今。Google 支付他的薪水来全职维护 Git。Git 从原型走向成熟，绝大部分的工作是他和社区完成的。

![](/images/tom-preston-werner-portrait.jpg)

**Tom Preston-Werner（1979–）** —— GitHub 联合创始人，"GitHub" 这个名字的提出者。2007 年 10 月在 Zeke's Bar 和 Chris Wanstrath 构思了 GitHub。2008 年拒绝了微软的 30 万美元留任 offer。GitHub 的 CTO 和 Chief Octocat。2014 年因骚扰指控辞职。

![](/images/chris-wanstrath-portrait.jpg)

**Chris Wanstrath（1985–）** —— GitHub 联合创始人兼前 CEO。写了 GitHub 的第一个 Rails 应用。主导了 GitHub 从创业公司到被微软收购的整个过程。2018 年收购时个人获利约 2 亿美元。

![](/images/pj-hyett-portrait.jpg)

**P. J. Hyett** —— GitHub 联合创始人（第三位）。负责 GitHub 的运营和社区管理。参与了定价策略、产品方向等关键决策。

**Scott Chacon** —— GitHub 联合创始人（第四位）。《Pro Git》作者，被翻译成 10 多种语言。负责 GitHub 的开发者关系和 CIO 角色。

**Simon Oxley** —— 英国图形设计师。在 iStock 上出售了 Octopuss 卡通图——被 GitHub 买断后改名 Octocat，成为全世界最知名的技术吉祥物。他也为 Twitter 设计了小鸟 logo。

![](/images/larry-mcvoy-bitkeeper.jpg)

**Larry McVoy（1962–）** —— BitMover 创始人，BitKeeper 的创造者。2002 年免费向 Linux 内核团队提供 BitKeeper，2005 年因 Tridgell 逆向工程而收回许可。这个决定间接催生了 Git。

![](/images/andrew-tridgell-samba.jpg)

**Andrew Tridgell（1967–）** —— Samba 项目创始人。编写了 SourcePuller 工具逆向 BitKeeper 协议，触发了 BitKeeper 许可危机。"Linus 在邮件里骂了我一遍，然后自己去写了一个更好的。"
