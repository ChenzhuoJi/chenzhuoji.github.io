## Hello World

```cpp
#include <iostream>
int main() {
    std::cout << "Hello, World!" << std::endl;
    return 0;
}
```

*这是 C++ 的 Hello World。和 C 的版本比起来，多了一行 `#include <iostream>`，多了一个 `std::` 前缀，多了一个 `<<` 运算符，多了一个 `return 0`。它从第一行代码就在告诉你一件事：我比 C 麻烦——但我知道自己在做什么。*

![](/images/iso-cpp-logo.svg)

*ISO C++ 官方标志——作为 C 语言的超集，C++ 在保留 C 高效、底层可控特性的基础上，加入了面向对象、泛型编程等现代特性，是游戏开发、高性能计算、系统编程领域的 “硬核工具”。*

1967 年，挪威的 Ole-Johan Dahl 和 Kristen Nygaard 在挪威计算中心完成了一件计算机史上被低估得最厉害的事情。他们发明了面向对象编程。

他们的语言叫 Simula——这个名字源自"Simulation Language"（模拟语言），因为它的初始目标就是做模拟：模拟银行排队、模拟交通流量、模拟工厂生产线。Simula 引入了一个革命性的概念：你可以把数据和操作数据的方法打包在一起，叫做"class"（类），然后基于它创建任意多个"对象"。你可以让一个类继承另一个类的特性，就像现实世界中汽车继承交通工具的特性一样。

这是人类第一次可以用代码来直接建模现实世界。你不再需要在一堆分散的函数和数据结构之间手动维护对应关系——你写一个 `class BankAccount`，它自己就知道怎么存钱、取钱、算利息。

但 Simula 有一个致命的问题。它太慢了。

Simula 的程序在运行时要做大量的动态检查——类型检查、空指针检查、数组边界检查。它的垃圾回收器会不定期地暂停整个程序来清扫内存。它的函数调用开销比汇编高出一个数量级。当你运行一个 Simula 程序时，机器的 CPU 有相当一部分不是在执行你的算法——而是在管理 Simula 本身的运行时系统。Dahl 和 Nygaard 在设计 Simula 时更关注表达的优雅，而不是执行的效率。这种事在学术界完全没问题，但在工业界——特别是系统编程的领域——这是一个死刑判决。

与此同时，另一个极端是 C 语言。C 快到极致——它生成的机器码几乎和手写汇编一样高效，没有运行时开销，没有隐性的检查，没有垃圾回收。你对内存的控制精确到字节。你想要一个指针操作一个地址，C 说"好的，给你"。但你用一个类来组织代码？C 说"什么是类？我没有这种东西。"C 在抽象层面的表达能力几乎是零。写 C 就是在操作内存和寄存器，只不过语法比汇编好看了那么一点。

这两种语言代表了两个世界。Simula 的世界：可以管理大规模复杂度，但性能代价大到无法接受。C 的世界：性能最好的，但代码规模一大就变成灾难——头文件里散落着一千个函数声明和结构体定义，没有任何办法把这些东西打包成有边界的模块。

能不能有一个语言，既要 Simula 的表达力，又要 C 的性能？

1970 年代末，一个丹麦博士生在剑桥大学写他的博士论文时，被这个问题折磨了很久。他喜欢 Simula 的 class 和继承——面向对象给他提供了组织大规模代码的思路。但他无法忍受 Simula 的性能。他试过在 Simula 里写他的分布式系统仿真，结果慢到他等不下去了。他改用 C 重写，性能上去了，但他又回到了"用 struct 和函数指针手动模拟面向对象"的原始状态——写和维护都令人痛苦。

他在某个深夜对自己说：我想要一种语言，既能像 Simula 一样组织程序，又能像 C 一样高效。

他决定自己造一个。

## 两张桌子之间

Bjarne Stroustrup 1950 年出生在丹麦奥胡斯的一个工人阶级家庭。父亲是当地的工厂工人，母亲是裁缝。家里没有学术背景，但 Stroustrup 从小就对各种工具和技术着迷——他拆过家里的钟表，鼓捣过收音机，用乐高搭过自己设计的东西。他后来在回忆中说："我不是那种从小就在电脑上编程的孩子——那时候根本没有个人电脑这种东西。我喜欢的是建造东西。"

1969 年他进入奥胡斯大学学数学和计算机科学。在那里他遇到了一个改变他一生的人——Kristen Nygaard。Nygaard 是 Simula 的共同发明人，经常从奥斯陆来奥胡斯大学讲课。Stroustrup 选修了 Nygaard 的课，第一次接触到了面向对象编程。"Simula 给我的震撼是它让我用完全不同的方式思考程序，"他后来写道，"程序不再是一系列指令的线性序列——它们是相互协作的对象，每个对象都有自己的数据和自己的行为。"

1975 年，Stroustrup 去了剑桥大学念博士，导师是 David Wheeler——图灵奖得主（冯·诺依曼架构的"von Neumann"之所以叫"von Neumann"，是因为 Wheeler 是几位奠基人之一，而"Wheeler"的发音太像 Wheeler 在他参与的 EDVAC 机器报告里写了著名的"First Draft"章节，这一段有不同的历史叙述，简而言之 Wheeler 是剑桥计算机实验室的奠基人之一）。Stroustrup 的博士课题是分布式系统的通信与控制，他在研究中大量使用 Simula 来做仿真——然后就被 Simula 的性能问题折磨得体无完肤。

1979 年，Stroustrup 博士毕业，加入了新泽西州 Murray Hill 的贝尔实验室。

贝尔实验室在 1970 年代末的氛围是不存在第二个地方的。这里有 Unix 和 C 的诞生地，有 Dennis Ritchie、Ken Thompson、Brian Kernighan、Doug McIlroy——这些人是计算世界的基础设施建筑师。Stroustrup 加入的是计算机科学研究中心，他的第一个项目是分析 Unix 内核在分布式环境下的性能。

这个项目让他再次直面了那个"两张桌子"的问题。他以系统程序员的身份分析 Unix 内核——代码里有无数的结构体、指针、函数指针数组——一切都暴露在全局命名空间里，没有任何封装，任何地方都可以修改任何数据结构。他需要一个更好的组织方式。但他需要的不是牺牲性能的 Simula——因为他在写的代码直接关系到内核的效率，每多一个间接调用都是不能接受的。

于是他在 1979 年做了一个看起来有些自相矛盾的决定：他要在 C 语言的基础上，加上 Simula 的类。

这看起来简单，实际做起来需要解决一系列严峻的问题。C 的编译模型——头文件、源文件、链接器——不支持类的封装。C 的类型系统——int、char、struct——不支持继承。C 的函数调用——静态绑定的、不能重载的——不支持多态。你要在 C 的所有限制之上，加上面向对象的所有能力，同时不让性能退步。

Stroustrup 开始在他熟悉的 C 编译器上做实验。他给自己的编译器取名 Cpre——C Preprocessor——因为它本质上是一个预处理程序：读取带有类的 C 代码，翻译成普通 C 代码，然后再由标准的 C 编译器编译。Stroustrup 添加的第一个特性是"classes"（类），然后是"derived classes"（派生类，继承的雏形），然后是"strong type checking"（强类型检查），"inline functions"（内联函数），"default arguments"（默认参数）。他管这个新东西叫"C with Classes"（带类的 C）。

1980 年 4 月，Stroustrup 在贝尔实验室内部传阅了一份备忘录，标题是《Classes: An Abstract Data Type Facility for the C Language》。这份备忘录是 C++ 的第一份正式文档。它的措辞非常谨慎——Stroustrup 不是在宣布一个新语言诞生，而是在描述"一种给 C 增加抽象数据类型支持的技术"。

C with Classes 的第一个实现不是编译器——是一个翻译器。它把 C with Classes 的代码转换成 C 代码，然后让 C 编译器去编译。这个选择是 Stroustrup 最关键的工程决策之一，也是 C++"既要也要"哲学的第一个具体体现：它意味着从第一天起，C++ 就可以使用所有 C 的库、工具、运行时支持。任何一个能跑 C 编译器的平台，都能跑 C++。不需要新的代码生成器，不需要新的优化器，不需要新的链接器。你写 C++ 代码，它先变成 C 代码——而且是高质量的 C 代码——然后再变成机器码。

但这也意味着 C++ 从一开始就背上了 C 的所有历史包袱。C 的数组和指针的混淆语义，C 的头文件机制，C 的预处理宏——所有这些都原封不动地继承了下来。Stroustrup 不是没想过改——但他做了一个他认为对整个项目生死攸关的决定：兼容性高于一切。"如果人们必须抛弃现有的 C 代码才能用我的新语言，"他后来说，"他们根本就不会给我一个眼神。"

这个决定后来被反复讨论——它是 C++ 成功的最大原因，也是 C++ 永远被诟病的最深根源。兼容 C 让 C++ 可以在 1980 年代迅速占领 C 的生态位，但也让这门语言永远无法简化自己的底层模型。这是"既要也要"的第一次显性化：既要拥抱 C 的生态系统，又要建立新的抽象层——但你没法同时获得两者的全部好处。

## 偷懒的翻译器

1982 年，Stroustrup 开始开发 C with Classes 的正式继任者。他需要一个更好听的正式名称了。

1983 年 12 月，贝尔实验室的同事 Rick Mascitti 在闲聊中提了一个建议。当时 C with Classes 已经有了几个候选名字——比如"new C"和"C with Classes"本身。Mascitti 说，为什么不叫 C++？"++"是 C 的自增运算符——意思是"比 C 更进一步"。

这个名字带着明显的玩笑意味——一个编程语言叫"自增运算符"？听起来像是某个黑客的冷笑话。但 Stroustrup 接受了。他说服自己的理由很务实："C++"这个名字简短、容易记住、而且暗示了和 C 的继承关系。1983 年 12 月，这个名字第一次出现在贝尔实验室的内部文档中。计算机史上永远改变了软件开发方式的名字，竟然来自同事的一个玩笑。

1984 年，Stroustrup 实现了第一个流 I/O 库——`<<` 和 `>>` 运算符的用法。这个想法来自 Doug McIlroy——正是当年在贝尔实验室提出 Unix 管道的同一个人。McIlroy 说，为什么不把输出变成一个运算符？这样你就可以写出 `cout << "Hello" << endl` 这样的链式表达式。这个语法设计后来成了 C++ 最广为人知的特征之一——喜欢它的人觉得它自然且可扩展，不喜欢它的人觉得它丑陋且反直觉。但无论如何，它完美体现了 C++ 的设计精神：让程序员定义运算符的行为，而不是让语言决定一切。

1985 年 10 月，C 语言的编译器历史上发生了一件大事。Stroustrup 发布了 Cfront 1.0——世界上第一个 C++ 编译器（严格来说是翻译器）。Cfront 读到 C++ 代码，产生 C 代码，然后由本地 C 编译器编译。这本身不是一个新技术——C with Classes 也是这么做的。但 Cfront 被包装成了真正的产品。

当时 Cfront 的定价非常有趣：商业使用要买许可证，但非商业使用只需要支付 75 美元——只收运费。如果你在一个大学教书或做研究，你花 75 美元就能收到一卷磁带，里面是 Cfront 的完整源代码。这个定价策略让 C++ 在学术圈里迅速传播。学生和教授们花几十美元就能获得全套工具，然后他们开始用 C++ 写课程项目、做实验、写论文。当这些学生毕业进入工业界，他们带着 C++ 来到公司。不到五年，C++ 就从贝尔实验室的内部项目变成了全世界的语言。

更令人惊讶的是 Cfront 本身的来历——它是用 C++ 写的。这是一个自举（bootstrapping）的故事：Stroustrup 先用手工写了一个最小的 C++ 编译器，然后用这个编译器编译 C++ 编译器自身，产生一个"新版本"的 C++ 编译器，再用这个新版本编译更完整的 C++ 编译器——如此迭代，直到语言特性全部实现。为了在没有 C++ 编译器的机器上也能编译 Cfront，Stroustrup 附带了"半预处理"过的 C 代码——那是 Cfront 的 C++ 源码被手工转换为 C 代码后的版本。Unix 社区的开发者拿到这份代码之后，可以用本地的 C 编译器先编译它，然后就能在本地运行 C++ 了。

![](/images/cfront-10-source-code-tape.jpg)

*Cfront 1.0 的源代码磁带，1985 年。非商业使用仅收 75 美元运费——这个定价策略让 C++ 在学术圈迅速传播。Cfront 本身是用 C++ 写的，附带了人工转换为 C 的源码，以便没有 C++ 编译器的机器能编译它。*

同一个月，Stroustrup 出版了《The C++ Programming Language》第一版。

![](/images/stroustrup-tcppl-first-edition-cover.jpg)

*《The C++ Programming Language》第一版（1985）。这本书在 C++ 编译器完全实现所有特性之前就出版了——Stroustrup 基于自己对语言未来形态的理解写了书，然后追着书去实现编译器。这种"先写书、后实现"的顺序在语言设计史上绝无仅有。*

这本书的写作顺序是反常规的：Stroustrup 在书中用到了当时 C++ 还没有完全实现的特性——他基于自己对语言未来形态的理解写了这本书，然后回头再去修改编译器来匹配书中的内容。"书在编译器之前出版"这件事，在编程语言设计史上几乎绝无仅有。

三件事在同一个时间点一起爆发——名字、编译器、书——C++ 告别了"C with Classes"的实验阶段，正式作为一门语言登上了舞台。

## 语言的青春期

1980 年代末到 1990 年代初，C++ 经历了迅速的演化。

1989 年，C++ 2.0 发布。这次更新的核心特征是多继承（multiple inheritance）——一个类可以同时继承多个基类。

多继承是 Stroustrup 从 Simula 发展出来的概念——Simula 事实上允许某种形式的多继承，但没有任何广泛使用的语言真正实现过。Stroustrup 认为多继承是有用的：比如你有一个"窗口"类和一个"可滚动"类——一个可滚动的窗口应该同时继承两者的特性。在单继承的世界里，你只能做"窗口 → 可滚动窗口"这样的一维继承；在多继承的世界里，你可以组合任意多个"方面"。

但问题随之而来。如果两个基类有一个同名的方法，派生类该调用哪个？如果两个基类都继承自同一个祖先，派生类里会有两份祖先的副本吗？这些问题在理论上可以被菱形继承（diamond inheritance）的虚拟继承来解决，但解决方式的复杂度吓坏了许多程序员。

多继承迅速变成了 C++ 最受争议的特性。Java 和 C# 的设计者明确拒绝了它——它们用"接口"（interface）来替代多继承，只允许继承行为规范，不允许继承实现。Java 首席架构师 James Gosling 后来直言："多继承是 C++ 最糟糕的地方之一。它带来的问题比解决的问题还多。"

但多继承只是 C++ 日益增长的庞大体量的一个侧面。1990 年，Stroustrup 和 Margaret Ellis 合著的《The Annotated C++ Reference Manual》（ARM）出版了。ARM 不是教你怎么写 C++ 的——它是一部 C++ 语言的"宪法律师版注释"：四百多页，逐条解释了 C++ 语法的每一个细节、每一个设计决策背后的理由、每一个可能引起歧义的角落。ARM 的厚度本身就说明了一个事实：C++ 已经不再是一本 228 页的书就能讲清楚的小语言了。

作为对比，K&R C 的参考手册不到 50 页。C++98 的最终标准将近 700 页。

C++ 的规模让它的用户群产生了分化。一部分人爱它——因为它在性能上不妥协，同时又给了他们足够强大的抽象工具。另一部分人恨它——因为要真正掌握 C++，你需要同时理解至少几个不同的"子语言"：C 的子集、面向对象的子集、模板的子集。每个子集有自己的规则和习惯用法，而它们的交互方式——比如模板和继承如何组合——更是一个深不可测的黑暗森林。

1991 年，Borland 发布了 Turbo C++——一个在 DOS 下运行的 C++ IDE。1992 年，微软发布了 Visual C++ 1.0。C++ 从贝尔实验室的研究工具变成了 PC 时代的工业标准。一个 25 岁的程序员可以在 Turbo C++ 的蓝色屏幕上写 Windows 3.1 的应用程序，用 OWL 或 MFC 框架来组织代码。面向对象不再是学术概念——它变成了每一个桌面应用的默认架构。

## 意外发现的编译时计算

1990 年代初，C++ 遇到了一个改变它命运的转折点：模板（templates）。

Stroustrup 最初设计模板的目的是解决一个非常具体的问题：类型安全的容器。在 C 语言里，如果你要写一个通用的"动态数组"或"链表"，你必须用 `void*`——一个指向"任何类型"的指针。但这意味着类型安全完全丢失：你可以不小心把字符串指针插到一个本应是整数数组的结构体里，编译器不会报错，运行时才会崩溃。

模板的语法很简单——`vector<int>`、`vector<string>`——你告诉编译器这个容器里装什么类型，编译器自动为你生成对应版本的代码。这是一个在编译时完成的工作：不需要运行时类型信息，不需要虚函数表的不必要的间接，性能零开销。

但模板很快被证明比 Stroustrup 想象的强大得多。模板本质上是一种"编译时参数化"机制——你不仅可以用类型作为模板参数，还可以用整数、用函数指针、用其他模板。这意味着你可以在编译时执行计算——不是"在运行时计算"，而是在编译器编译你的代码时，让编译器来算。

1994 年，C++ 标准委员会的一次会议上，一位名叫 Erwin Unruh 的德国程序员做了一个演示——他写了一个 C++ 程序，用模板在编译时计算素数。程序本身不能正常编译——它在"编译错误"中输出素数序列。用户故意写下一个错误的表达式，编译器在报错信息中打印出计算过程中的数值，这些数值恰好是素数。整个会议室安静了下来，然后是一片哗然。

模板元编程（template metaprogramming）就这样被意外发现了。原来 C++ 的模板系统是图灵完备的——你可以在编译时做任何计算，只要你的程序足够复杂、编译时间足够长。一个程序员可以在编译时计算出斐波那契数列，让生成的机器码直接包含计算结果，而不是在运行时计算。

这个发现让 C++ 的"既要也要"达到了一个新的高度：你可以在编译时做原本只能在运行时做的事情——而且不消耗任何运行时性能。模板元编程成了一个狂热的研究领域。人们用模板写矩阵库，在编译时检查矩阵维度是否匹配；用模板写状态机，在编译时确保所有状态转移都是合法的；用模板写表达式模板（expression templates），优化矩阵运算的中间结果，让 `A = B + C * D` 这样的表达式在编译时就完成优化，而不是在运行时为每个中间变量分配空间。

但模板也有代价：编译时间暴涨，编译错误信息变成了天书。如果一个模板嵌套了五层，其中某一层的类型不匹配，编译器输出的错误信息可能长达几百行，充斥着编译器内部的类型名称，人类几乎无法阅读。"模板错误信息"成了 C++ 程序员最大的噩梦之一——也是 C++ 复杂性的标志性症状。

## 改变命运的库

C++ 最重要、最被热爱的部分，其实不是 Stroustrup 设计的——甚至不是任何语言设计者设计的。

Alexander Stepanov 1950 年出生于莫斯科，在莫斯科大学学习数学。他的学术背景让他对算法的通用性和抽象性有着极其深刻的追求。Stepanov 的核心信念是：算法应该与数据结构分离。一个好程序员不应该为"整数数组排序"和"字符串链表排序"写两个不同的排序函数——应该有一个通用的 `sort` 函数，它操作某种"迭代器"（iterator），而迭代器是容器和算法之间的桥梁。

这听起来像是常识——今天的程序员看 C++ 的 `std::sort(v.begin(), v.end())` 觉得理所当然。但在 1980 年代，这个想法是激进到荒谬的。当时的主流编程范式是面向对象——把所有东西捆绑在一个对象里（"vector"知道自己怎么排序，"list"知道自己怎么排序）。Stepanov 说：不要这样——让算法独立，让容器独立，用一个薄薄的抽象层（迭代器）把它们连起来。

他管这叫"泛型编程"（generic programming）。

Stepanov 在惠普实验室（HP Labs）工作期间，花了大量时间研究如何在不同的编程语言中实现这种范式。他试过在 Ada 里做，在 Scheme 里做，都不满意——要么性能不够好，要么类型系统不够强。1987 年，他在一次 C++ 标准委员会的会议上遇到了 Andrew Koenig，后者告诉他 C++ 正在加入模板。Stepanov 觉得这是他一直等待的机会。

1993 年 11 月，Stepanov 在圣何塞的 C++ 标准委员会会议上展示了他和同事孟 Lee（Meng Lee）合作开发的一个库——Standard Template Library，STL。他只用了很短的时间做了一个演示：`sort(v.begin(), v.end())`——一行代码，对一个动态数组进行排序。算法和容器解耦，不需要继承，不需要虚函数，不需要手动实现排序代码。

委员会的反应是压倒性的。Andrew Koenig 在看到演示之后坚决推动这个提案的快速审批——他意识到这是 C++ 标准库自流 I/O 之后最大的进步。1994 年 7 月，STL 被正式纳入 C++ 标准草案。一个月后，HP 将 STL 的实现免费发布在互联网上——正好赶上 1995 年互联网的商业化起飞。全世界的 C++ 程序员同时发现了 STL。一夜之间，C++ 的标准库从一个简陋的集合（`iostream`、`string`、几个容器）变成了一个庞大的基础设施：`vector`、`list`、`deque`、`map`、`set`、`sort`、`find`、`binary_search`——以及连接这一切的迭代器。

STL 改变了 C++ 的方向。在 1990 年，C++ 还是一个"带类的 C"，用来写 GUI 应用程序和游戏引擎。1995 年之后，C++ 成了一门可以进行高阶泛型编程的语言——你在 STL 的范式里看到的不是面向对象，而是"算法 + 数据结构通过迭代器连接"的抽象。这个范式后来影响了 Java 的 Collections Framework、C# 的 LINQ、Python 的 itertools、Rust 的 Iterator trait。但 STL 在 1994 年做出来的这些设计，至今仍然是标准库设计的巅峰之一——因为它没有在性能和抽象之间做任何妥协。

Stepanov 的故事有一个让人唏嘘的后半段。STL 是 C++ 的"第二主角"——它不是 Stroustrup 设计的，但它定义了现代 C++ 的灵魂。Stepanov 后来离开 HP，加入 Adobe，又加入 Microsoft，继续推广泛型编程的思想。但 STL 的影响远远超出了 C++ 本身——它实际上重新定义了"标准库"应该长什么样。C++ 的成功有一半属于 Stroustrup，另一半属于 Stepanov。前者给了语言生命，后者给了语言灵魂。

## 标准化：六年的马拉松

1989 年，ANSI 启动了 C++ 的标准化进程（1991 年加入了 ISO）。标准委员会是一个几十人——后来发展到几百人——的大型群体，成员来自编译器厂商、大学研究团队、工业界用户，当然还有 Stroustrup 本人。

标准化是一个政治和技术并行的过程。每一个特性都要经过提案、辩论、投票。争议最激烈的话题包括异常处理（exception handling）、运行时类型识别（RTTI）、名字空间（namespace）、以及模板的完善细节。

异常处理的争论焦点是性能代价——C++ 的"零开销原则"在异常机制上遇到了挑战。异常处理意味着编译器必须在每一个可能抛出异常的地方插入额外的代码——哪怕你这个程序从来不抛异常，运行时代码里也带着异常处理的隐形成本。Stroustrup 坚持"零开销原则"不能妥协：不使用的特性不应该有代价。最终 C++ 的异常处理实现采用了"零开销异常处理模型"（Zero-Cost EH）——在正常执行路径上没有任何额外开销，代价全部转移到异常路径（和代码体积）。这个方案在技术上优雅，在实现上非常困难。

名字空间的争论焦点则是兼容性——已有的 C++ 代码没有使用 `namespace`，整个标准库的符号全部暴露在全局命名空间里。委员会在如何引入命名空间而不破坏已有代码的问题上反复讨论了数年。最终方案——`using namespace std;` 的折中——让很多人不满意，但它至少让标准库的符号有了一个逻辑上的范围。

1998 年，C++98 正式发布——ISO/IEC 14882:1998。这份标准厚达 700 多页。C 语言的 ANSI 标准不过 200 页。经过了将近十年，C++ 终于有了一个"官方确定的版本"。

![](/images/cpp-standards-committee-march-1996-santa-cruz.jpg)

*1996 年 C++ 标准委员会在圣克鲁兹的会议现场。Stroustrup 站在左侧。后排中间的年轻人们不会想到，他们参与定义的语言会统治系统编程世界三十年。1998 年，C++98 正式发布——700 多页的标准锁定了语言的复杂性，也锁定了它的影响力。*

但标准化也有一个很多人没有预见到的副作用：锁定了复杂性。C++98 标准化之后，C++ 的进化速度急剧下降。下一个大版本 C++11 等了整整 13 年。在这 13 年里，语言没有大的变化，但世界在变化——Java 在 1995 年发布了第一个版本，C# 在 2000 年诞生，Python 和 Ruby 在快速成长。C++ 的社区在 2000 年代的前半段弥漫着一种焦虑：语言是不是停下来了？是不是被超越了？

实际情况比看起来复杂。C++98/03 确实统治了企业级 C++ 开发长达十年——Windows、Office、Adobe、Oracle、金融交易系统、游戏引擎——所有对性能有极致要求的地方，C++ 仍然是唯一选择。但语言的停滞意味着编译器厂商之间出现了分化：各家在自己的产品里添加了扩展，交叉编译变得越来越困难。标准委员会在很长时间里谨慎到几乎不做事——因为加入一个新特性需要投票，而任何被拒绝的提议都可能让厂商不满。

2000 年代末，情况开始改变。新的标准委员会领导层推动了一个激进的决定：设定 2011 年为 C++ 下一个版本的死线。不管到时候有没有准备齐全，就在那一年发布。这个"不发布就永远不发布"的压力让 C++11 成为了 C++ 史上最大的版本——它几乎在每一个方面都扩展了语言的能力：自动类型推导（`auto`）、范围 for 循环（`for (auto x : v)`）、lambda 表达式、智能指针（`shared_ptr`、`unique_ptr`）、右值引用和移动语义（move semantics）、可变参数模板、初始化列表、constexpr。C++11 发布之后，整个社区松了一口气——C++ 没有死，它回来了。

从那以后，C++ 进入了三年一版的节奏：2014（C++14）、2017（C++17）、2020（C++20）、2023（C++23）。每一版都在增加新特性，也在增加语言的总复杂度。

## "既要也要"的代价

C++赢了。它赢得了系统编程世界。

Google Chrome、Microsoft Windows、Adobe Photoshop、Unreal Engine、MySQL/MariaDB、TensorFlow 的底层运行时——全是 C++。你的手机在跑 C++ 编译的代码（Android 的底层、iOS 的内核驱动），你的路由器在跑 C++，你的游戏机在跑 C++，你的汽车的电子控制单元在跑 C++。如果你是一个生活在 2026 年的人，你遇到的每一次数字交互——从手机亮屏到银行转账到社交媒体刷新——背后都有 C++ 代码的部分参与。

它做到了"既要也要"：兼顾性能与抽象。它证明了这是可能的。

但代价是多少？

第一，语言复杂度。C++ 是目前主流语言中学习曲线最陡峭的，没有之一。一个新手程序员第一次面对 C++ 时，他需要理解至少五层不同的"子语言"：C 的子集（指针、数组、宏、头文件）、面向对象的子集（class、继承、虚函数）、模板的子集（`vector<T>`、模板特化）、STL 的迭代器和算法、以及 C++11 以来引入的现代特性（lambda、移动语义、智能指针）。每一层都有自己的惯用法和常见陷阱。它们之间的交互方式更是深不可测——模板和继承的混合、异常安全与资源管理的博弈、编译时编程的诡异边界。C++ 的学习曲线不是一条曲线——它是一面悬崖。

第二，编译错误。模板元编程创造了一种两难：越强大的 C++ 代码编译越慢、编译错误信息越难读。一个典型的 C++ 模板错误信息可能长达几百行——编译器会把模板实例化的完整路径打印出来，包括所有中间步骤的类型名称。你可以在这些错误信息里走失很久。C++ 社区用了几十年的时间才通过 Concepts（C++20）来缓解这个问题。

第三，模块化迟滞。C++ 的头文件机制直接从 C 继承过来。头文件的包含顺序、宏定义、条件编译——所有 C 时代的问题完整保留。C++ 的分类编译模型（每个 `.cpp` 文件单独编译，然后链接）导致了业界最慢的编译速度之一——Google 的 Chromium 代码库全量编译可能需要几个小时。模块（modules）直到 C++20 才正式加入语言标准——距离 C++ 的诞生已经过去了 35 年。

第四，也是最深层的矛盾：安全。C++ 的"零开销原则"背后的代价是把安全责任全部交给了程序员。C++ 不保护你。它不像 Java 那样阻止你访问越界的数组，不像 Rust 那样在编译时检查谁借了谁的指针，不像 Python 那样在运行时检测类型错误。C++ 说："你让我做什么我就做什么。你让我写 `a[1000]` 而 `a` 只有 10 个元素——好，我去读那个地址的内存。你说那个内存是什么，它就是什么。"

这个"信任"的代价是惨重的。Microsoft 的安全响应中心在过去十年里反复报告：Windows 中约 70% 的严重安全漏洞是内存安全问题——缓冲区溢出、use-after-free、野指针——几乎全是 C/C++ 的"勋章"。2014 年的 Heartbleed（心脏出血）漏洞是 OpenSSL 中一个简单的缓冲区边界检查缺失——用 C 写的，全世界一半的 HTTPS 服务器在几周内被打上了补丁。Google 的 Project Zero 团队在 Chrome、Android、Linux 内核中发现的大量 0-day 漏洞，绝大多数根源是 C/C++ 的内存错误。

2025 年 3 月，Stroustrup 在 Bloomberg 的一次采访中罕见地发出了公开呼吁："我要求 C++ 社区保卫这门语言。"他的背景是 Rust 正在快速蚕食 C++ 的生态位——Linux 内核接纳了 Rust，Android 支持了 Rust，美国国防部和网络安全局公开建议新项目使用内存安全语言。2024 年，白宫发布了正式的《内存安全报告》，把 C/C++ 列入了需要被替代的"非内存安全语言"清单。Rust 的 Stroustrup 的"既要也要"的承诺——Rust 说"既要 C++ 的性能，也要编译时的内存安全"——而它的答案是所有权系统。这个答案正在被越来越多的人接受。

Stroustrup 不是没有看到问题。他在 2015 年启动了 C++ Core Guidelines 项目，联合了 Herb Sutter 等社区领袖，编写了一套安全编码规范，配合静态分析工具（如 Microsoft 的 C++ Core Checker）来检测常见的内存错误。这套指南是至今为止对 C++ 安全问题的"最认真的回应"——但问题是，一个像 C++ 这样庞大的语言，没法用指南来解决问题。指南只是建议，不是强制。你可以在 C++ Core Guidelines 的规范下写安全代码，但你也可以在同一个编译器里写完全不安全的代码。编译器的态度始终没有变过：你要做什么，我就做什么。

## 没有银弹

1987 年，Fred Brooks 发表了那篇著名的《没有银弹》（No Silver Bullet），断言在可预见的未来，没有单一的技术突破能带来软件生产力数量级的提升。C++ 的历史可以被解读为对"银弹"的漫长追逐：面向对象是不是银弹？似乎不是——代码还是要写，bug 还是要改。泛型编程是不是银弹？也不是——模板元编程的兔子洞深不见底。自动内存管理是不是银弹？C++ 至今没有垃圾回收——因为它承诺了"你不需要的就不付代价"。

但 C++ 的历史也可以被读作另一个更温柔的故事：一个设计者在三十年的时间里，面对"既要也要"的永恒张力，没有选择放弃任何一端。他没有说"算了，我们放弃性能，加个垃圾回收吧"。也没有说"算了，抽象太复杂了，我们回到 C 吧"。他坚持要把两张桌子拼在一起——哪怕拼出来的桌面上会有裂缝，有人觉得它太丑，有人觉得它太危险。

Stroustrup 后来在《The Design and Evolution of C++》的前言里写了一段话，可能是对 C++ 遗产最诚实的描述：

> "C++ 并非一个完美的语言——我不认为存在完美语言这种东西。而且在可预见的未来，我也不认为我会看到一种。我的主要目标是创造一种能帮助程序员解决实际问题的语言——不必是一种完美的语言，但必须是实际可用的语言。"

它不完美。但它可用。它在四十年里让无数人写出了操作系统、浏览器、游戏引擎、交易系统、数据库、编译器、深度学习框架。它让"大规模代码"变得可能——尽管代价是让这门语言本身变得庞大到几乎无法被任何人完全掌握。

这不是一篇技术的失败说明——这是一篇关于野心的注脚。

"既要也要"的代价，就是 C++ 的胜利和它的伤痕来自同一个地方。没有这个野心，C++ 不会成为 C++。它可能是另一个更好的、更简洁的、更安全的语言——但它不会是 C++。

*Bjarne Stroustrup（1950–），C++ 的创造者。丹麦奥胡斯人，工人阶级家庭出身，从 Kristen Nygaard 本人那里学到面向对象编程。剑桥博士毕业后加入贝尔实验室，1979 年开始"C with Classes"的工作。1983 年改名 C++，1985 年发布第一个商业编译器。设计哲学的核心是"零开销抽象"——你不为不用的特性付出代价。2018 年获 Charles Stark Draper Prize（美国工程院最高奖）。*

![](/images/alexander-stepanov-portrait.jpg)

*Alexander Stepanov（1950–），STL（Standard Template Library）的设计者，泛型编程的伟大倡导者。俄裔美国计算机科学家，莫斯科大学数学背景。在惠普实验室开发了 STL，1994 年提交给 C++ 标准委员会。他的理念是"算法应该与数据结构分离"——用迭代器作为桥梁。STL 定义了现代 C++ 的"灵魂"。*
