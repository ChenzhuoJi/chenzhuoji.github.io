## Hello World

```sql
SELECT 'Hello, World!';
```

*这是 SQL 的 Hello World。没有变量声明，没有函数定义，没有循环。你写一个词 `SELECT`，再写你要的东西——数据库就给你答案。这是人类第一次可以"问"计算机一个问题，而不是"命令"它去找。*

![](/images/sql-logo.png)

*这是 SQL（结构化查询语言） 的标志性图标。左侧的圆柱形代表数据库的存储形态，右侧的 `sql` 字样则点明了它的核心 —— 用于管理和查询关系型数据库的标准语言。自 1986 年成为 ANSI 标准以来，SQL 一直是操作关系数据库的唯一通用语言。无论底层是 MySQL、PostgreSQL、Oracle 还是 SQLite，你问数据库的方式没有变：`SELECT`。*

1969 年，一个程序员坐在 IBM System/360 的终端前。他面前的屏幕上一片漆黑，光标在左上角闪烁。他接到了一个简单的任务：查出上个月买过牙膏的所有客户。

在 2026 年，你可以在一秒钟之内写完这条查询——甚至在手机上打开一个 App，点几个按钮就能搞定。但 1969 年，这个程序员面对的是一个 CODASYL 网络数据库。他必须手写一段 COBOL 程序。先打开客户文件，沿着指针链找到第一个客户记录，然后遍历这个客户的订单链表——每次沿着 NEXT 指针跳到下一笔订单——然后从每笔订单里找出对应的产品记录，检查产品名称是不是"牙膏"。如果是，记下客户编号，回到订单链表继续走。走完所有订单之后，再回到客户文件，找到下一个客户，重复整个过程。

这不是比喻。这是真正的代码。你不是在"查"数据库，你是在用指针在一张巨大的网状图里"航海"。每一步都要精确知道你在哪个记录、哪个指针、哪个字段。写错一个指针的名字，程序崩溃。漏掉一个条件分支，数据错误。更糟的是，如果你的老板下周说"顺便把上个月买过洗衣粉的客户也列出来"，你得重新写一遍——不是在查询后面加一个条件，是重写整个导航路径。

数据存在。每一笔订单、每一个客户、每一种产品——整整齐齐地躺在磁盘上。但是你要取出来，必须自己找到路。这就像一个图书馆，所有的书都有，但入口处只给你一串走廊编号，你不认识任何一个书名。你每次找书都要先走一遍走廊，记住每个转弯的位置，下次换一本书又要重新走一遍。

Fortran 解决了"怎么让科学家自己写程序"的问题。Lisp 解决了"怎么让计算机处理符号"的问题。C 解决了"怎么用高级语言写操作系统"的问题。但 1969 年的商业计算世界面临着一个全新的问题：数据就在那里——但你怎么把它取出来？能不能让用户直接说"我要什么"，而不是"怎么去找"？

SQL 的答案是：能。一句 `SELECT` 就够了。

但这句话花了将近二十年才变成现实。这二十年里，有一个英国数学家在 IBM 内部孤军奋战，一个 27 岁的天才在读完自己的论文后几周突然去世，两个项目在工业界和学术界赛跑，一个创业者在巨头犹豫不决的时候抢走了市场——而所有这些人的努力，最终凝结成了一句七行字的英语句子，改变了一切。

## 指针迷宫

要理解 SQL 的革命性，你需要知道它要取代的是什么。

1960 年代的数据库世界由两种模型主导。第一种是 IBM 的 IMS——层次数据库。IMS 的故事本身就是计算史上的一章：它是为阿波罗计划开发的。NASA 需要管理土星五号火箭的零部件清单——成千上万个零件，每个零件属于一个子系统，每个子系统属于一个更大的系统。IMS 用"树"来表示这个结构：一个根记录下面挂着一层子记录，子记录下面再挂一层。这种结构非常适合零件清单——"土星五号 → 第二级 → J-2 发动机 → 燃料阀门"——你从根出发，一层一层往下走就能找到你要的东西。

但真实世界的数据不是树。一个客户可以下多笔订单，一笔订单可以包含多个产品，一个产品可以被多个客户购买。这是"多对多"的关系。IMS 处理多对多关系的方法是在数据中重复——一个产品记录可能会在多个订单下面各存一份。这意味着数据冗余、更新困难、一致性堪忧。

第二种模型是 CODASYL——网络数据库。1969 年，数据系统语言会议（CODASYL）的数据库任务组发布了一套标准，用"系"（set）的概念来连接记录。你可以定义一个"客户-订单系"，让客户记录"拥有"一组订单记录；再定义一个"订单-产品系"，让订单记录"拥有"一组产品记录。然后通过在记录之间嵌入指针——一个记录里存着另一个记录的磁盘地址——来构建一个网络。1973 年，Charles Bachman，网络模型的先驱，获得了图灵奖。他的 IDS（Integrated Data Store）是第一个商用的网络数据库系统。

在纸面上，网络模型能表达任意复杂的数据关系。在实际中，它的代价是程序员要为每一次数据查询写一段"导航"代码。Bachman 自己的《图灵奖演讲》里有一张著名的幻灯片，展示了一个程序员在 CODASYL 中查数据时的思维过程——一长串的问号和箭头，每一步都要做决策："我现在在哪个记录里？我从哪条指针过来的？我下一步要去哪？"

那个时代的数据库编程，本质上就是在做链表遍历——和你在 C 语言里手写一个单向链表的插入删除没什么区别，只不过数据在磁盘上、指针是磁盘地址、每一步都可能触发一次 I/O。一个简单的"列出买了牙膏的客户"，放在今天一个没学过数据库的基础班学生都能五分钟写出来的查询，在 1969 年是一个需要几天的编程任务。

导航式数据库的哲学是：数据库是一个藏宝迷宫，程序员是寻宝者，数据库系统的职责是帮你保管好迷宫——但你自己要找路。Codd 要做的，是把迷宫变成一个地图册。你不需要走进去，你只需要问："地图册第 47 页上的那个城市，它的邮编是多少？"

## 飞行员与数学

Edgar "Ted" Codd——他在 IBM 内部被叫做 Ted，但他在论文上签的是正式的名字 Edgar F. Codd——不是一个典型的计算机科学家。事实上，他用了将近二十年才走到数据库这个领域。

1923 年，Codd 出生在英格兰波特兰岛——一个位于英吉利海峡的岩石岛屿，以采石业著称。他在 Poole Grammar School 读书，然后进了牛津大学的 Exeter College 学数学和化学。1941 年毕业时，二战正在最激烈的阶段。他报名加入了皇家空军的海岸司令部，驾驶桑德兰水上飞机——一种四引擎的大型巡逻机，机身上长满了炮塔，一次任务可以飞行十几个小时，在北大西洋上搜索德国的 U 型潜艇。他在军队里升到了飞行中尉。

战后，Codd 做了一个奇怪的转折。1948 年，他搬到了纽约，加入 IBM——不是以研究员的身份，而是做一个"数学程序员"。这个头衔在当时基本就是计算机操作员的文雅说法——写机器语言的代码、操作穿孔卡片、把程序塞进机器。但在 IBM，他的天赋很快被注意到了。他参与了 IBM 701 和 702 的开发，写了最早的数学子程序库。

但 Codd 在美国的生活并不平静。1953 年，麦卡锡主义到了最歇斯底里的时期。Codd 虽然出生在英国，但他父母是左翼——他父亲是一个皮件工坊的经营者，母亲是裁缝。不管具体原因是什么，Codd 对美国政治氛围极度反感。他搬到了加拿大渥太华，为 IBM 的加拿大分公司工作。直到 1957 年麦卡锡倒台、政治气氛缓和之后，他才返回美国。

1957 年回到 IBM 美国后，Codd 做了一个重要的决定：他要去读博士。他进了密歇根大学安娜堡分校，师从 John Holland（遗传算法的发明者），研究细胞自动机的自我复制——这是一个从 von Neumann 延伸出来的课题：能不能用一组简单的规则，让一个计算系统自我复制？Codd 的博士论文证明了一个理论结果：在二维细胞自动机中，八个状态就足以实现通用计算和通用构造。这是一个漂亮的数学结果，1965 年他拿到了博士学位。

1967 年，Codd 加入了 IBM 在圣何塞的新实验室——IBM 圣何塞研究实验室（后来改名为 Almaden 研究中心）。实验室刚成立不久，团队不大，研究方向自由。Codd 已经有了一个他想了很久的问题：数据管理能不能---用数学来做？

他不是工程师——他是数学家。工程师关心的是"能不能跑起来"、"性能怎么样"。数学家关心的是"形式化是否正确"、"有没有统一的模型"。Codd 带着这种气质走进了数据管理的领域。他环顾四周，看到的是一团混乱：IMS 是树，CODASYL 是图；指针遍地都是，遍历路径各不相同；同一个查询在不同的系统上写出完全不同的程序。这不是一个"成熟的技术"，这是一个还没有找到统一理论的手艺活。

Codd 认为，他能给这个领域的东西，和一个数学家能给任何领域的东西一样：一组清晰的、基于集合论的定义。关系、元组、属性、键——不需要指针，不需要导航路径，不需要程序员在脑海里画图。所有数据都表达成一种统一的形式：关系——就是数学里那个"集合"的概念。

1968 年，Codd 在 IBM 内部撰写了一份报告，初步勾勒了关系模型的轮廓。1969 年，他在 IBM 内部的研讨会上做了一次演讲。听众的反应？冷漠。IBM 的人不觉得有什么问题——IMS 卖得不错，CODASYL 正在标准化。为什么要推翻一切从头来过？

但 Codd 没有停下来。

## 一篇被冷落的论文

1970 年 6 月，《Communications of the ACM》发表了一篇 13 页的论文，标题长且直白：《A Relational Model of Data for Large Shared Data Banks》。作者：E. F. Codd。

这篇论文可能是数据库领域历史上被引用次数最多的文献之一。今天任何一个数据库从业人员——不管你用的是 MySQL、PostgreSQL、Oracle 还是 SQLite——你使用的系统在概念上都源于这篇论文的某个段落。

论文的开篇就直击要害：

> 本文试图建立一个数据模型，它基于集合论中的关系概念，使用户能够以高度的独立性和一致性来观察数据，而无需关心数据的物理表示或访问路径。

"无需关心数据的物理表示或访问路径"——这句话就是在挑战整个导航式数据库的根基。Codd 的意思很清楚：用户应该面对的是一个逻辑视图，而不是物理结构。用户看到的是"关系"（表），而不是指针链。用户操作的是"关系代数"（选择、投影、连接），而不是导航路径。

论文中，Codd 把数据组织成"关系"（relations）——你可能更熟悉它的俗名"表"（table）。每个关系是一个元组的集合——你叫它"行"（row）和"列"（column）。用户通过"关系代数"来操作这些数据：选择（选出某些行）、投影（选出某些列）、连接（把两个关系按某些条件合并）、除（一个稍微复杂的操作，用于回答"谁买了所有产品"这类问题）。

Codd 在 1971 年的后续论文中定义了"关系完备性"——一个数据库语言至少要能表达全部的关系代数操作，才算是真正的"关系型"。这是一条清晰的底线。在那个充斥着各种自创查询语言的世界里，Codd 画了一条线。

但 1970 年的学术界和工业界都没有立刻拥抱这篇论文。学术圈的反应是好奇但谨慎——有几个大学的教授读到了它，觉得"有点意思"。工业界的反应更直接：IBM 忽视了自己的研究员。

原因很简单。IBM 正在大卖 IMS。IMS 是 IBM 最赚钱的产品之一，为阿波罗计划和无数企业客户提供了可靠的数据管理。IBM 的决策层担心：关系模型会不会蚕食 IMS 的市场？如果一个客户可以用一种"更简单"的方式查询数据，谁还愿意花大钱买 IMS 和那些昂贵的培训服务？

这不是猜测。IBM 内部确实有人说了这样的话。Codd 的提案被要求"再做做研究，等到它成熟了再考虑"。IBM 的"Future Systems"项目——一个试图统一 IBM 所有产品线的庞大计划——虽然包含了关系数据库的子系统（System R），但项目领导层故意把 Codd 排除在外。他们不想让 "那个数学家" 来指导工程开发。

Codd 在 IBM 内部的处境变得尴尬。他发表了计算机史上最重要的论文之一，但 IBM 不想用它。他试图说服同事，但大多数人不愿意听。Christopher Date —— IBM 的研究员，后来成为 Codd 最坚定的合作者——回忆说："Ted 在 IBM 内部是孤立的。他不是那种善于在政治上周旋的人。他相信正确的理论最终会胜出。"

但 Codd 的孤立没有阻止另一个地方的人捡起了他的论文。

## 两个世界

1970 年代初，两个团队几乎同时开始把 Codd 的理论变成可以运行的软件。一个在 IBM 内部，名叫 System R。一个在加州大学伯克利分校，名叫 Ingres。它们的路线的差异——和创造者的性格差异一样大。

System R——"R" 代表"Relational"——是 IBM 圣何塞实验室在 1974 年正式启动的项目。IBM 终于承认关系模型不是"再研究研究"就能糊弄过去的东西——伯克利的团队已经在动手了——但管理层的态度仍然暧昧。项目预算不充裕，团队不大。更重要的是，Codd 被刻意排挤在外。System R 的技术领导是 Frank King 和后来加入的 Donald Chamberlin，不是 Codd。

Codd 有自己的语言想法——他设计了一个叫 Alpha 的查询语言，基于关系演算。但 System R 团队觉得 Alpha 太数学化了——它用到了量词（∀ 和 ∃）、下标符号、上标符号。对程序员来说都难看懂，对商业用户简直就是天书。他们决定走另一条路。

与此同时，在伯克利，Michael Stonebraker 和 Eugene Wong 读到了 Codd 1970 年的论文。Stonebraker 当时是伯克利的助理教授，研究兴趣是数据库系统。他后来回忆说："我读了 Codd 的论文，那就像——'啊，这才是对的。'"他和 Wong 决定做一个自己的关系数据库。

Stonebraker 和 Wong 有一个现成的项目可以做幌子：他们本来在做一个叫 Ingres 的地理信息系统（Interactive Graphics Retrieval System），给自己的经济学课题组管理数据。他们决定把这个项目的资源挪去搞关系数据库。Ingres 这个名字保留了下来——但在新的上下文里，它变成了"University INGRES"：一个研究性质的关系数据库系统。

Ingres 有 System R 没有的三个优势。第一是自由——伯克利是学术界，不受 IBM 的商业压力影响，可以做任何实验。第二是开放——Ingres 的源代码只收一个名义上的费用就可以获取，学生们成群结队地用它、读它、修改它。第三是 Unix——Ingres 跑在 DEC 的 PDP-11 上，操作系统是 Unix，而 Unix 正在学术界迅猛传播。

到 1970 年代末，Ingres 已经在一千多个站点上运行。它被下载、被改造、被用作教材。Stonebraker 和他的学生们在 Ingres 上做了大量开创性的工作：查询优化、并发控制、事务管理。

但在最关键的设计决策上，System R 和 Ingres 走向了不同方向：查询语言。Ingres 用 QUEL（Query Language）——一种更接近关系演算、数学风格更浓的语言。System R 用 SEQUEL——一种更接近英语、试图让非专业用户也能理解的语言。

这个选择后来决定了整个数据库行业的方向。

## SEQUEL——英语风格的查询语言

1973 年，Donald Chamberlin 从 IBM 位于纽约 Yorktown Heights 的 Watson 研究中心调到了圣何塞。他 29 岁，斯坦福大学电机工程博士，研究方向是数据库系统。到圣何塞之后，他被分配的任务是：给 System R 设计一种查询语言。

Chamberlin 不是从零开始的。他和另一位刚加入 IBM 的研究员——Raymond Boyce——一起工作。Boyce 比 Chamberlin 小两岁，普渡大学计算机博士，专长也是数据库。两个人年龄相仿、兴趣一致，很快形成了默契。

他们最初的尝试叫做 SQUARE——Specifying Queries As Relational Expressions。SQUARE 的语法大量使用数学下标和上标符号——因为它本质上是在模仿关系演算的记号。比如一个查询可能写成这样：

```
SUPPLIER.SNAME WHERE (σ.S# = S.S# ∧ σ.CITY = 'London')
```

写论文可以，做产品不行。Chamberlin 和 Boyce 很快就意识到，SQUARE 对非技术用户太不友好了。商业世界的数据查询——银行、保险公司、零售连锁——用户是会计师、文员、仓库管理员。这些人不想看到数学符号。他们想要的东西是：一句普通的英语句子。

于是他们在 SQUARE 的基础上做了第二次设计，把数学符号换成了英语单词。他们把新语言叫做 SEQUEL——Structured English Query Language。

SEQUEL 的设计哲学可以概括为：让查询读起来像英语。三个关键词构成了它的骨架：

- `SELECT`——你要什么
- `FROM`——从哪拿
- `WHERE`——条件是什么

把这句英语说出来，就是"从某某表中选择某某字段，当某某条件成立"。一个实际的查询：

```
SELECT NAME
FROM CUSTOMERS
WHERE CITY = 'London'
```

读出来就是："Select name from customers where city equals London"。这几乎是英语口语了。不需要懂集合论、不需要懂指针、不需要懂磁盘存储——一个仓库管理员都能理解。

当然，SEQUEL 的设计远不止这三个关键词。它包含了你今天在 SQL 中看到的大部分核心概念：`INSERT`、`UPDATE`、`DELETE`、`CREATE TABLE`、`DROP`、`GRANT`、`REVOKE`。还有那个让无数开发者头痛但不可回避的 `NULL`——表示"未知"的三值逻辑。

1974 年 5 月，Chamberlin 和 Boyce 在 ACM SIGMOD 研讨会上发表了 SEQUEL 论文。论文的标题是《SEQUEL: A Structured English Query Language》。它的引言清晰地阐述了设计动机：

> 大多数数据库系统的用户并不是专业程序员。他们更没有兴趣去学习复杂的导航式数据操作语言。一种适用于这样的用户的查询语言，应该以一种方便而且自然的语法来表达查询——并且这种语法应该足够灵活，允许具有不同技术背景的用户在经过最少的训练后使用。

这篇论文中的 SEQUEL 和今天的 SQL 有一些明面上的差别：它用 `U` 代替了 `UNION`，用标点符号而不是关键词来做某些限定。但它的灵魂——SELECT-FROM-WHERE——和今天完全一致。论文中展示了第一个完整的 SEQUEL 查询示例，查询客户表中 city 为"London"的客户姓名。这个例子放在今天任何一个 SQL 教程的第一章里都不会显得过时。

论文发表了。Chamberlin 和 Boyce 很高兴。System R 团队有了语言规范，可以开始认真实现了。

一个月后，1974 年 6 月 18 日，Raymond Boyce 在家中因突发动脉瘤去世。

他 27 岁。留下妻子 Sanndy 和襁褓中的女儿 Kristin。

Chamberlin 后来在接受口述历史采访时说："Ray 的去世对我的影响极其深远。我们共同设计了 SEQUEL，我们处在一个非常激动人心的探索阶段。然后他突然就不在了。"他停顿了一下。"我在他的追悼会上，看到他的女儿——她太小了，还不明白发生了什么。"

Raymond Boyce 只做了不到两年的数据库研究。他的职业生涯——从 1972 年拿到博士学位到 1974 年去世——总共不到 24 个月。但在这 24 个月里，他做了三件事：和 Codd 一起发明了 Boyce-Codd 范式（BCNF），这是数据库规范化理论的核心成果；和 Chamberlin 一起设计了 SEQUEL，这成了世界标准；以及——他走了。

BCNF 以他和 Codd 的名字命名。SQL 以他和 Chamberlin 为设计者载入史册。27 年的人生，两行不朽的贡献。

Chamberlin 独自继续了 SEQUEL 的开发。后来因为"SEQUEL"这个名称已经被一家英国飞机公司（Hawker Siddeley）注册为商标，SEQUEL 改名为 SQL。官方的发音是 "S-Q-L"（逐个字母读），但全世界大量程序员仍然叫它 "sequel"。Chamberlin 本人说两种发音都可以——他看到人们仍然在用"sequel"，心里其实有些暖意。

## 如何问问题

SQL——无论你叫它 "sequel" 还是 "S-Q-L"——和之前的查询方式最本质的区别不是语法，是思维方式。

在导航式数据库中，你告诉计算机怎么找数据。在 SQL 中，你告诉计算机你要什么。怎么找到，是计算机的事。

这个思维方式的核心是"声明式编程"（declarative programming）。这是编程语言史上最被低估的概念转折之一。Fortran、Lisp、C 都是"命令式"的——你写一条一条的指令，告诉计算机每一步做什么。SQL 说你只需要描述结果，计算机自己决定执行路径。

`SELECT NAME FROM CUSTOMERS WHERE CITY = 'London'`——你描述的是结果："名叫 London 的城市的所有客户名字"。你不需要说"打开 CUSTOMERS 文件，读取第一条记录，检查 CITY 字段是否等于 London，如果是则输出 NAME 字段，然后读取下一条记录，重复直到文件末尾"。计算机自己决定怎么做。

这意味着计算机可以帮你做优化。如果你在 CITY 列上建了一个索引，查询优化器会自动选择用索引而不是全表扫描。不需要改代码。不需要通知程序员。索引是后来加的，查询语句不需要变。在导航式数据库的世界里，如果你加了一个新的索引路径，你得重写你的导航代码才能利用它。

这也是 SQL 的另一个微妙设计：用表（表）而不是文件（文件）作为存储的基本单位。"表"是一个逻辑概念——一个表由行和列组成，没有指针，没有链接，没有层级。用户不需要知道数据在磁盘上是怎样存放的。今天是 B-tree，明天可能是哈希表，后天可能是列式存储——但你的 SQL 查询不需要改变。

Codd 管这叫"数据独立性"（data independence）。他说这应该是数据库系统的第一原则。应用程序不应该依赖数据的物理存储方式。如果你改变了物理存储，应用程序不应该需要修改。这在导航式数据库中是根本无法想象的——你的 COBOL 程序里每一个 `NEXT` 指针都绑定了一个物理实现。

但"声明式"也意味着 SQL 把执行效率的控制权交给了数据库系统本身。你不再能精确控制每一步的执行顺序。这对程序员来说有时需要信任——信任数据库优化器会做出好的决策。在 System R 之前，这是一个大胆的赌注：一个自动的查询优化器真的能比手写导航路径快吗？

## 查询优化器——数学变成了工程

System R 最被低估的贡献不是 SQL，而是查询优化器。

1979 年，Pat Selinger 领导的 System R 团队发表了一篇论文——《Access Path Selection in a Relational Database Management System》。这篇论文描述了 System R 的查询优化器，它基于成本的优化策略，使用动态规划算法来选择最优的执行计划。今天所有关系数据库的优化器——Oracle、MySQL、PostgreSQL、SQL Server——都可以追溯到这篇论文。

查询优化器要解决的核心问题很简单：给定一个 SQL 查询，数据库系统有多个不同的执行方式。比如连接四个表 `A JOIN B JOIN C JOIN D`，实际上有多少种不同的连接顺序？答案是 (4!) = 24 种。每种连接顺序还可以选择不同的连接算法（嵌套循环、哈希连接、排序合并连接）和不同的访问路径（全表扫描、索引扫描）。组合爆炸出来的可能性可能有几百上千种。优化器的任务是从中选出成本最低的一种。

Selinger 的团队想出的办法是动态规划。他们给每种执行方式估算成本——成本公式综合考虑了 CPU 时间、I/O 次数、内存使用等。然后从最底层开始，一层一层往上构建最优方案：先找出访问单个表的最优路径，然后找出两个表连接的最优路径，再找出三个表连接的……每一步都只保留最优的少数几个方案，剪掉明显差的选择。

这个算法在 1979 年的论文里被完整地描述了出来。它的核心洞察是：连接操作的"交换律"和"结合律"意味着不同的连接顺序产生相同的逻辑结果——但性能可能差几个数量级。一个自动化的、基于成本的优化器可以替用户做出这个选择。

这对 SQL 的可行性至关重要。如果 SQL 的"声明式"理念意味着用户放弃了对执行路径的控制，那么数据库系统就必须提供一个足够聪明的优化器来弥补。没有优化器，SQL 就是慢的——比手写导航代码慢得多。有了优化器，SQL 在某些情况下甚至可以和手写汇编一样快。

System R 的优化器证明了：自动化的查询优化不只是可行的，它经常能选出比人更好的执行计划——因为它能评估程序员想不到的路径组合。

System R 团队还做了许多其他开创性的工作：多版本并发控制（MVCC）、事务的 ACID 属性、崩溃恢复机制、SQL 预处理器。你可以说 System R 是"世界上第一个真正完整的关系数据库系统"——它证明了关系模型不只是一个理论玩具，它可以处理真实世界的商业工作负载。

但 System R 有一个致命的问题：IBM 不卖它。

## 抢在 IBM 前面

从 1974 年到 1978 年，System R 在 IBM 内部运行得越来越好。1977 年，它迎来了第一个外部客户——Pratt & Whitney，飞机制造商——开始在真实的工程环境中使用 System R。1978 年，IBM 在几个客户站点进行了试运行。反馈非常好——客户们说"这比 IMS 简单多了"。

但 IBM 的高层在犹豫。

他们的犹豫是完全可以理解的。IMS 仍然是 IBM 数据库业务的现金牛。关系数据库会蚕食 IMS 的市场吗？答案是几乎肯定的。而且 System R 当时还不稳定，性能在某些场景下不如 IMS。IBM 的产品部门不愿意把一个"研究项目"包装成产品。IMS 团队的领导层也不愿意看到内部竞争。

IBM 的犹豫给了外面的人一个机会。

1977 年，Larry Ellison 在硅谷读到了 IBM 关于 System R 的论文。他当时 33 岁，已经从 Ampex 辞职，和 Bob Miner、Ed Oates 一起创立了一家叫 Software Development Labs 的小公司。他看到了一个他一生中最清晰的商业机会：IBM 发明了关系数据库——但它不卖。那我来卖。

Ellison 的策略大胆而简单：抢在 IBM 前面发布产品。他们的公司——1979 年改名为 Relational Software, Inc.（后来改名为 Oracle）——把 IBM 论文中描述的概念转化为产品。他们用的语言是 SQL（那时还没改名，但 Ellison 的团队直接沿用了 SEQUEL 的理念）。第一个版本叫 Oracle V2——虽然它实际上是公司的第一个产品，但"V2"听起来更成熟。

1979 年，Oracle V2 在 VAX 计算机上发布了。严格来说，它是世界上第一个商用的 SQL 关系数据库——比 IBM 自己的 SQL/DS（1981）早了两年，比 DB2（1983）早了四年。

但 Oracle V2 是一个不完整的产品。它没有真正的事务处理——没有 commit/rollback。它的性能很差。它的 bug 很多。Ellison 的销售团队非常激进——有时甚至承诺了产品没有的功能。但它的存在本身就是一个信号：关系数据库不是学术玩具了。你可以买到它了。

Ellison 赌对了三件事：第一，企业客户迫切想从 CODASYL 和 IMS 的迷宫中逃出来，哪怕换成一个不完美的关系数据库；第二，IBM 不会因为 Oracle 的先发优势而放弃关系数据库——IBM 的反应是在 1981 年仓促发布 SQL/DS，然后在 1983 年发布 DB2；第三，SQL 会赢——一旦 IBM 也支持它，整个行业就会倒向它。

赌对这三件事的 Ellison 把 Oracle 从圣克拉拉的一个小平房变成了全球最大的数据库公司。但这个故事的讽刺性在于：Codd 在 IBM 内部写了那篇论文，IBM 不想用它；Chamberlin 和 Boyce 在 IBM 内部设计了 SQL，IBM 慢悠悠地实现它；然后 Ellison——一个局外人，读了 IBM 的论文，在 IBM 犹豫的三年窗口期里，抢走了整个市场。

计算机史上的"企业创新困境"没有比这更经典的案例了。

## 语言战争

到 1980 年代初，关系数据库已经是一个确认可行的技术方向——但用哪种语言来查询它，还没有定论。

IBM 推 SQL。Ingres 推 QUEL。

QUEL 是 Stonebraker 设计的——它是 Ingres 的原生查询语言。从技术角度看，QUEL 比 SQL 更接近 Codd 的关系演算。它更简洁、更正交、语义上更清晰。一个 QUEL 查询的例子：

```
RANGE OF C IS CUSTOMERS
RETRIEVE (C.NAME)
WHERE C.CITY = 'London'
```

和 SQL 比，QUEL 的一个优势是它没有 `SELECT` 的歧义——`SELECT` 在 SQL 中既担当"选出列"（投影）的功能，又担当"选出值"（有时甚至是表达式计算）的功能。QUEL 用 `RETRIEVE` 做投影，用 `WHERE` 做选择，分工明确。

Stonebraker 和他的团队坚信 QUEL 是更好的语言。数据库界的很多研究者也这么认为——QUEL 在技术上更干净、更一致。从 1974 年到 1984 年，Ingres 用户社区里几乎只用 QUEL。

但 SQL 有一个 QUEL 没有的东西：它读起来像英语。

这个看起来"肤浅"的优势，在商业世界里被证明是决定性的。你要卖给银行和保险公司——一个非技术背景的经理看了 SQL 的 `SELECT ... FROM ... WHERE`，他大概能猜出这句话在干什么。他看了 QUEL 的 `RANGE OF ... RETRIEVE`......也能看懂，但不如 SQL 直观。而且 SQL 有一个更关键的优势：IBM。

1986 年，美国国家标准协会（ANSI）发布了第一个 SQL 标准（SQL-86）。选择 SQL 而不是 QUEL，不纯粹是一个技术决定。IBM 的游说力量——IBM 是标准委员会里的大玩家——起了作用。SQL 在先发市场上已经有了几年的领先（虽然 Oracle 的产品不完善，但它确实是第一个）。而且 SQL 的"英语风格"对标准委员会的成员有天然的吸引力，他们觉得它更容易被非技术用户接受。

Ingres 在 1986 年之后不得不做了一个痛苦的转变：放弃 QUEL，支持 SQL。Stonebraker 后来在口述历史中承认，这是一个商业决定——标准走了 SQL 方向，Ingres 必须跟着走。但他始终认为 QUEL 是技术上更优越的语言。

这场语言战争的结果决定了未来三十年的数据库格局。SQL 赢了——而且赢得非常彻底。今天，几乎每一门数据库课程都教 SQL。几乎所有的主流数据库系统——Oracle、MySQL、PostgreSQL、SQL Server、SQLite——都支持 SQL。QUEL 变成了一个历史脚注。

但这场战争还有一个安静的代价：Codd 的失望。

Codd 在 1985 年发表了一篇著名的文章，后来被称为"Codd's 12 Rules"——一个真正的"关系型"数据库管理系统必须满足的 12 条规则。Codd 的目的一方面是区分"真正的"关系数据库和那些只加了关系模型的皮毛的商业产品；另一方面，也是在纠正 SQL 对他的关系模型的偏离。

因为 SQL 不是"纯粹"的关系语言。它允许重复的行（关系数学定义中不允许重复的元组）。它的 NULL 处理——三值逻辑——偏离了关系模型的闭合原理。它没有真正支持域（domain）——关系模型中每个属性都应该有一个明确的域定义。SQL 的实现让这些偏离变成了标准。

Codd 在 1990 年出版的《The Relational Model for Database Management: Version 2》中，用了大量篇幅逐一纠正 SQL 中的"错误"。他列出了关系模型的 333 条规则。他坚持认为 SQL 只实现了"大约 98%"的关系模型——而那 2% 的差距，他耿耿于怀了一辈子。

1990 年，Codd 离开了 IBM。他和 Chris Date 一起创办了一家咨询公司，致力于推广"真正"的关系模型——一个比 SQL 更纯粹、更严格、更数学化的版本。但市场已经做出了它的选择。SQL——这个"98%"的解决方案——已经统治了世界。

Codd 在 2003 年去世。他没有看到 NoSQL 的运动——新一代的开发者开始质疑"表"和"行"和"关系"是否总是最好的数据模型。但这是另一个故事了。

## 遗产——SELECT 改变了一切

SQL 是计算机语言史上最独特的成功故事。

它不是给程序员写的——或者说不只是给程序员写的。它是给所有需要和数据打交道的人写的。会计师、市场分析师、产品经理、运营人员——只要会写 `SELECT`，你就拥了了和数据库对话的能力。在 SQL 之前，问数据需要写一段几十行的 COBOL 程序。在 SQL 之后，问数据只需要一句英语短句。

`SELECT` 可能是人类历史上被书写次数最多的代码片段。它在每一条数据分析的背后、在每一个报表的背后、在每一个电商购物车的背后、在每一次银行转账的背后。它安静地工作，不被注意——就像 C。

SQL 影响了后来几乎所有的查询语言。XML 的 XQuery 借鉴了 SQL 的 SELECT-FROM-WHERE 结构。语义网的 SPARQL 本质上是用 RDF 三元组替代了表的 SQL。GraphQL 的名字就包含了"QL"——Query Language。NoSQL 运动的数据库们——MongoDB、Cassandra、Couchbase——他们的查询语言都在不同程度上模仿了 SQL。有些（如 Couchbase 的 N1QL）几乎是 SQL 的方言。

但 SQL 的统治地位也有阴暗面。标准化走的太慢——SQL-86 之后有 SQL-89、SQL-92、SQL:1999、SQL:2003……每次标准发布间隔几年，而数据库厂商的实现在这几年的空白期里各自为政。结果是：Oracle 的 SQL 方言、SQL Server 的方言、MySQL 的方言、PostgreSQL 的方言——它们共享 SQL 的核心语法，但在细节上处处不同。从一个数据库迁移到另一个数据库，从来不是一件轻松的事。ISO 标准规定了 SQL 应该如何行为，但厂商们在标准之外做了大量扩展，用"性能"和"差异化"做借口，把用户锁在自己的生态里。

NULL 的三值逻辑——SQL 中的 `NULL` 既不等于任何值，也不等于其他 `NULL`。`NULL = NULL` 的结果是 `NULL`——不是 `TRUE`，不是 `FALSE`。这意味着 `WHERE X = NULL` 永远选不出任何行。你必须写 `WHERE X IS NULL`。这个设计让无数初学者（和有经验的开发者）抓狂，但它根植于 Codd 的原始逻辑——"未知"不代表"假"，"未知"和"未知"不一定相等。

还有那个 Codd 一直耿耿于怀的问题：SQL 允许重复的行。在严格的关系模型中，一个关系是一个"集合"——集合里没有重复元素。但 SQL 的表默认允许重复行。你可以用 `DISTINCT` 去掉重复，但默认是有重复的。Codd 认为这是一个根本性的偏离——它意味着 SQL 里的"表"不完全是"关系"，而是一个"多重集"（bag）。这个偏离在 1974 年的 SEQUEL 设计里就是有意的——Chamberlin 和 Boyce 认为去掉重复行会增加查询的计算开销，而且某些场景下用户确实想看到重复。但 Codd 从不接受这个理由。

SQL 不是完美的。但它"足够好"。足够好到被世界采纳，足够好到统治三十五年的数据库市场，足够好到让一门编程语言——一个非程序员也能使用的声明式查询语言——成为一个 IT 从业者的基础技能，而不是一个需要专门培训的专家的狭窄领地。

## 从计算到查询

Fortran 让科学家自己编程。Lisp 让机器处理符号。C 让操作系统可移植。SQL 让商业用户自己查数据。

计算机从"计算工具"变成了"数据管理工具"。这是商业计算的核心转折点。在 SQL 之前，数据是程序的附属品——你写一个程序，程序里嵌入了数据操作逻辑，数据只能通过程序来访问。在 SQL 之后，数据是独立的——它自己存在一个"数据库"里，任何有权限的人都可以用 SQL 来查询它，不依赖于特定的程序、特定的语言、特定的机器。

数据独立于程序。这比听起来要深刻得多。它意味着一家公司的数据不再锁在某个程序员的 COBOL 代码里——它存放"在数据库中"，可以被多个应用程序共享、可以被分析师查询、可以被决策者快速访问。数据变成了企业资产，而不是代码的副产品。

这个转变的后果是：人们开始产生前所未有的海量数据。因为"问问题"变得太容易了，每个人都想多问几个。会计问上个月的应收账款，市场部问上一次活动的转化率，产品经理问新增功能的用户留存——每个人都在写 SELECT。

SQL 降低了数据查询的门槛，但这也意味着数据开始爆炸。1970 年代，一家银行的数据库可能有几十万条记录。1990 年代，几百万条。2000 年代，几十亿条。到 2026 年，全球每天产生几百拍字节的新数据。当每个人都在写 `SELECT`，当数据从 GB 变成了 TB 变成了 PB——我们怎么存储、怎么查询、怎么管理前所未有的大规模数据？

那是下一章的故事了。

SELECT * FROM HISTORY WHERE LANGUAGE = 'SQL';

结果只有一行。但这一行改变了世界。

## 人物

![](/images/edgar-codd-portrait-young.jpg)

*Edgar "Ted" Codd（1923–2003），关系模型之父。英国出生，牛津学数学化学，二战飞桑德兰水上飞机的 RAF 飞行员。1967 年加入 IBM 圣何塞实验室。1970 年发表关系模型论文。1981 年获图灵奖。他是数学家，不是工程师——他相信"数据管理应该用集合论，而不是指针遍历"。*

![](/images/don-chamberlin-portrait.jpg)

*Donald D. Chamberlin（1944–），SQL 的共同创造者。斯坦福博士，1971 年加入 IBM Research。和 Raymond Boyce 一起设计了 SEQUEL/SQL。1974 年 Boyce 去世后独自继续 SQL 的开发。后来还领导了 XQuery 的设计。2009 年从 IBM 退休后加入 Couchbase。至今仍在硅谷活跃。*

![](/images/raymond-boyce-portrait.jpg)

*Raymond F. Boyce（1946–1974），SQL 共同创造者。普渡大学博士，1972 年加入 IBM。和 Chamberlin 一起发表了 SEQUEL 论文。1974 年 6 月因动脉瘤去世，年仅 27 岁。留下妻子和襁褓中的女儿。BCNF（Boyce-Codd 范式）以他命名。24 个月的职业生涯，创造了一门统治世界的语言。*

![](/images/michael-stonebraker-portrait.jpg)

*Michael Stonebraker（1943–），UC Berkeley 教授，Ingres 项目的领导者。读到 Codd 的论文后决定自己做关系数据库。Ingres 用 QUEL 语言和 SQL 打了一场"语言战争"。后来还做了 Postgres（PostgreSQL 的前身）。2014 年获图灵奖。*

![](/images/larry-ellison-young-1970s.jpg)

*Larry Ellison（1944–），Oracle 公司的创始人。读到 IBM 关于 System R 的论文后，意识到关系数据库的商业潜力。1977 年成立 Software Development Labs，1979 年发布 Oracle V2——比 IBM 自己的 SQL/DS 还早两年。"抢在 IBM 前面"的策略造就了全球最大的数据库公司。*

![](/images/pat-selinger-portrait.jpg)

*Pat Selinger，System R 查询优化器团队的领导者。1979 年发表了基于成本的动态规划优化器论文——今天所有关系数据库优化器都源于这篇论文。她让"声明式查询"变得高效可行，是 SQL 能够成功的幕后关键人物。*
